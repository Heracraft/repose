## host-02, end to end

Install 2m27s, post_install 37s, join_token 1s, availability alert 2m1s,
`Apply complete! Resources: 4 added, 0 changed, 1 destroyed`, RC=0. The
45m deadline never fired. Seats went from 4 to 28, "total from 2 ready,
undrained hosts: memory allows 35, cores allow 28". A small guest was
created on it through the api, booted, reported `e2e-host02`, 1 core and
3 GB, reached https://example.com with 200, and was destroyed.

It could not register itself. Both `hostd` and `repose-register` failed
on `register: join token already used` -- the token was spent by the
26 October attempt that hung. Recovered by hand: `repose-admin hosts add
--name host-02 --reissue`, the token written to `/run/repose/join-token`,
then the two units started. A tainted install replays but a spent token
does not reissue with it, so any install that reaches the api and then
fails leaves the next attempt dead on arrival. Open, with the install
lane. Note for whoever takes it: after registering, the host's sshd moves
off the VNet address to WireGuard only, so the operator path changes
mid-recovery -- host-02 is reachable at 10.255.0.4.

## A correction to what this release was thought to leave open

I recorded that I-866 did not protect the running control VM and that the
2026-10-26 outage was one reboot away. That was inferred from
`ignore_changes = [source_image_reference, custom_data]` in the coolify
module, without looking at the machine, and it is wrong. Verified
read-only on the box: `/etc/wireguard/wg0.conf` carries
`ListenPort = 51820` with mtime 2026-10-26 17:27:03, so the restore that
day was a persisted file edit and not a runtime-only `wg set`;
`wg show wg0 listen-port` is 51820; `wg-quick@wg0` is enabled and active,
so the unit reads that file at boot; and the stale generator
`/usr/local/sbin/repose-wg-setup` cannot revert it, because
`edge_public_key` was empty when its `custom_data` was rendered on
2026-09-20 and it reaches `if [ -z "" ]` and exits before its
`cat > /etc/wireguard/wg0.conf`.

What is actually owed is repo-side: nothing records that the running
control VM is covered by that hand edit plus an inert generator rather
than by I-866's template, so the next reader concludes it is covered for
the wrong reason. A check in `ops/checks` asserting the live listen port
is 51820 would make it monitored rather than remembered. Not proved
empirically: that the port survives an interface restart. That is derived
from the unit plus the file; nobody restarted `wg-quick@wg0`, because it
is the one action here that can drop the tunnel and there is no second
control plane.

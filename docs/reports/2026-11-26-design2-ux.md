# Design 2 UX on the Mac: D1 baseline and candidates, 2026-11-26

d2-lab (measurer) for the design-2 program (`~/briefs/design2-program-2026-11-26.md`).
Every number here was measured on one Mac, at the UTC times given, with the
instrument named. A number with no run behind it is not in this report. Raw data:
`/mnt/nixstore/sharing/d2-lab/data/` on woker-1 (CSV and JSONL per measure, named in
each table), scripts in `/mnt/nixstore/sharing/d2-lab/bin/`.

## What was measured

- Mac: AWS mac-m4.metal, eu-west-1b, M4, 10 cores, 24 GiB, macOS 15.8.3 (24H241), public
  34.244.167.107. GUI auto-login as ec2-user, session unlocked, screen lock off, display
  sleep 0 (set by d2-arch at 11:46Z, before anything of repose was installed). So D1 ran in
  the logged-in, unlocked state a desk Mac has, not EC2's default headless state.
- D1 = today's release, installed as a customer would: `curl -fsSL
  https://repose.run/install.sh | sh -s -- --version v0.1.66` (CLI v0.1.66 darwin/arm64),
  then `repose host add e2e-mac2` (vfkit 0.6.4, appliance 2026.11.26.1, defaults: 8 vCPU,
  18432 MiB, 100 GB `disk.raw`, LaunchDaemon `run.repose.appliance`). Joined to the
  owner's production account with a private one-hour owner CLI session (minted into a
  private `XDG_CONFIG_HOME` on woker-1 and on the Mac, re-minted every 40 min, shredded at
  the end; never printed).
- The "laptop" is woker-1 (Azure, the CLI v0.1.66 linux/amd64 from the release, checksum
  checked), as in the sharing lab: `repose run`, `ssh <slug>.repose` and `repose attach`
  go through repose's edge gateway.
- Repos: fresh clones of the owner's `recruiting`, `unwrap` and `pocketmail`, push URL
  `DISABLED-NO-PUSH`, under `/mnt/nixstore/sharing/d2-lab/repos/`. Machines:
  `e2e-recruiting`, `e2e-unwrap`, `e2e-pocketmail` (and `e2e-pm-as1..3` for restore --as).
- Workloads, from the sharing lab (`/mnt/nixstore/sharing/lab/harness/guest/`, copied to
  `d2-lab/guest/`): **H** = recruiting turbo build + unwrap `next build` + pocketmail tsc
  and vite, clean each time with warm package caches; **P** = `go build -a -p $(nproc) std
  cmd` with an empty GOCACHE. A first H on each machine is a warm-up and is not counted.
- Instruments: bash `$EPOCHREALTIME` on woker-1 around each CLI command and ssh probe;
  perl `Time::HiRes` on the Mac (clock skew Mac minus woker-1 0.27 s, rtt 0.23 s, 14:59Z);
  a pty timer (`attachtime.py`, `firstscreen.py`) for attach and agent first screens;
  `repose ls` every 30 s (`states.log`); a Mac sampler every 5 s (`mac.csv`: per VZ
  process RSS and `top` footprint, vm_stat, swap, pressure, load).
- Sharing the Mac: d2-arch ran prototype VMs beside D1 all session (two idle 4 GiB VZ
  VMs most of the time). Its memory hog 12:53:00-12:56:30Z (macOS swap to 11.3 GB)
  overlapped the first install and first create, so those were rerun (measure 1, n=3,
  14:59Z on). Windows are in `~/briefs/design2-program.log`.

## Candidates

One candidate could be driven as a customer by 15:50Z: **D2n skeleton** on host
`e2e-d2n` (d2-runtime branch 3c23e89e: darwin hostd, Swift VZ launcher, launchd job per
machine, APFS volumes and clones; VZ NAT and d2-runtime's lab hub tunnel, NOT yet d2-net's
userspace network). Its edge path was not wired: `repose run` reported `did not answer
ssh in 60 s ... environment is not accepting connections yet` 3 of 3 times, so the
checkout was never copied and nothing that needs ssh could be measured on it. The "D2n
skel." column holds what the CLI alone could time (`d2n.csv`, 15:41-15:50Z); every other
design-2 cell is empty until the integrated e2e-d2n is handed over. Prototype figures that
d2-arch and d2-runtime measured themselves are theirs, not mine, and are not in the tables.

## Findings first

1. **Three busy machines on D1 is not a working state on this Mac.** With three H builds at
   once, the memory guard stopped `e2e-unwrap` in round 1 (13:37:17-47Z); with three P
   builds (Go, low memory) it stopped `e2e-unwrap` again (14:03:54-14:04:54Z). `repose ls`
   showed the three machines at 1.4-2.3 GB used (H) and 0.4-0.8 GB used (P) just before,
   against an 18 GB appliance. So the guard fired far below what `MEMORY` reports.
   Cause unverified: the appliance's own meminfo was not sampled (no way into it from this
   install); guest page cache counted as used is the first thing to check (`repose ls`
   MEMORY is the guest's view, the guard reads the appliance's).
2. **D1 never froze an idle machine on this Mac.** 0 of 6 machine-waits showed `frozen`:
   `e2e-recruiting` 12:59-13:17Z (17 min), `e2e-recruiting` and `e2e-unwrap`
   14:18-14:45Z (27 min, guest loadavg 0.00 at the end), all three 15:14-15:35Z (21 min). Cause unverified (the api's
   `rest_verdicts` are not readable from here; `nix/hosts/default.nix` defaults
   `pauseIdle = true`). Measure 4's D1 column is therefore "no freeze".
3. **macOS never gets the appliance's memory back while it runs.** The VZ footprint of the
   appliance rose 7.9 GB (12:56Z) -> 15 GB (12:59Z, three machines up) -> 18 GB (13:19Z,
   builds) and stayed 18 GB to the 14:15Z restart; after a restart, 4.1 GB with three idle
   machines (14:47Z), 7.6 GB after one H build, still 7.63 GB 4 min after every machine
   was stopped (14:50-14:54Z). Nothing returns until the appliance process ends.
4. **No park on any restart path.** Apple-menu restart (n=2) and `sudo shutdown -r now`
   (n=1): the launcher logs `stopping: the appliance parks its machines and powers off`
   and `stopped` in the same second, and every machine came back with a new boot_id.
   Separately the launcher logged `park-key: event=key_unavailable ... security
   add-generic-password: exit 195 ... Write permissions error` 89 times by 14:17Z, with the
   GUI session logged in and unlocked: the I-1394 park key cannot be made from the
   LaunchDaemon context even on a logged-in Mac.
5. Smaller, for the D1 record: `repose host add` prints `about 200 MB` for the image, the
   docs say about 85 MB; `snapshots restore --as` ends `it is running (large).`, a size on
   own hardware, where the docs say no line names a size; the join argument stays on disk
   after the join (`~/Library/Application Support/repose/join-argument`, 0600, 340 bytes,
   not read); install.sh could not put `~/.local/bin` on PATH because EC2's `~/.zshrc` is
   root-owned (an EC2 artefact, not a customer's Mac).

## Not run, and why

- Long attach across a minute of Mac sleep (5): an EC2 Mac has no way to wake it from
  here, and D1 holds a caffeinate assertion while machines run (`pmset`: "sleep prevented
  by caffeinate"); not risked.
- Claude Code `run -p` and the login share (6, 13): no Claude login on e2e-mac2.
- hostd update, power loss (no AWS calls allowed), disk nearly full, pool full (12, 14):
  not run in the time; the pool-full test would also have taken ~70 GB of the APFS
  volume d2-arch shares.
- The appliance's own memory (meminfo, cgroups): no runner inside this appliance; the
  sharing lab's runner was installed by hand and was not repeated.
- Three warm creates (2): two measured.
- Every D2n cell that needs ssh, attach, the checkout, builds, the network, or the agent:
  e2e-d2n's edge path was not wired at 15:41-15:50Z. Freeze/rest, park through repose,
  memory and the network on D2n wait for the integrated handoff.

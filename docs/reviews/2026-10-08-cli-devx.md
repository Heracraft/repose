# repose CLI: developer experience (2026-10-08)

On day 1, `repose run` in a checkout creates the machine, boots it, syncs the checkout and attaches, with no questions. Errors name the next command. The first hour has extra steps. You log in to Claude inside tmux, detach, and type `repose run` a second time. The quickstart skips the plan step. By day 50, reattaching costs little and ports forward with no command. `repose questions` covers every project. The daily loop breaks in three places:

- You cannot see from the laptop if the agent committed.
- `attach` cannot open the agent window that needs you.
- A size change or a fork can stop your agents and then fail the plan check.

These three changes matter most:

1. Add a git line to `status`, and fetch before `stop` snapshots.
2. Add `attach --window`, and name the window in `questions` and `ps`.
3. Check the plan before any step that stops a machine or takes a snapshot.

Bugs are in `reports/2026-10-08-cli-ergonomics-critique.md`. This report cites them by id (for example B4, C1, G7) and does not file them again.

## Scorecard

| Dimension | Grade | Reason |
|---|---|---|
| Mental model | B- | One verb and a fetch-only git remote carry the loop. Five ways to work in parallel, and "project" against "machine", blur it. |
| First hour | C | About 10 actions from install to a working agent. The list includes a manual Claude login, a second `run` and a plan step that the quickstart leaves out. |
| Daily flow | C+ | Reattach is fast and questions are one command. Attach cannot target a window, agent git state is hidden and `stop` takes one project. |
| Consistency | B- | Flags are shared between commands and success lines use one grammar. Scope, undo verbs, time formats and the list flags differ from command to command. |
| Feedback | C | Progress lines are good. `status` leads with host and IP, agent states use three vocabularies, and `logs --kind ops` drops results. |
| Discoverability | C | The typo engine and the in-guest command-not-found handler are good. Root help has no docs link, completion setup is hidden, and config.toml has no command. |
| Peer conventions | B | `exec`, `cp`, the SSH host and `--json` match peer CLIs. There is no `whoami` and no token login, and `ssh CMD`, `open L:R`, `-p` and `logs --tail` all fail. |
| Confidence | C+ | `rm` has a real undo. `resize --size` and `fork` stop or snapshot before the plan check, and `--discard-remote` deletes with no copy. |

## Strong points

**Starting and coming back**
- `cd repo && repose run` finds the project from the git remote. In the common case you never type a project name. No `link` step comes first, as it does with `vercel link` or `railway link`. A second laptop needs no setup.
- `run` is idempotent, so retyping it costs nothing. `devpod up` and `vagrant up && vagrant ssh` are the closest peers.
- Your working state goes up: uncommitted changes, unpushed commits, untracked files, gitignored `.env` files and the gh, Codex and opencode logins.
- `run` refuses before it creates anything that would fail, and the refusal gives the fix. For example: `Your checkout has no commits yet, so there is nothing to sync. Commit once (git add -A && git commit -m init) and run again, or pass --no-sync.` (exit 2).
- `run` on a running machine does not sync over the agent's tree. It says `Not synced: your laptop has work the machine doesn't (3 modified, 1 untracked, 2 commits)`.
- With the SSH master up, `repose attach` makes no API call (fastpath.go:14-25). After a Wi-Fi drop it reconnects for up to 2 minutes with the screen intact.

**Getting work back**
- `run` adds a fetch-only `repose` remote, so `git fetch repose` and `git log main..repose/main` are commands you know. `git push repose` fails with a sentence that names `repose sync`. `git fetch --all` skips the remote, so a stopped machine does not break your usual fetch.

**Reaching the machine**
- `<project>.repose` is an SSH host. `ssh`, `scp`, `rsync` and VS Code Remote work with no `repose` command first, and `ssh-prepare` renews certificates.
- `repose exec -it psql` copies the `docker exec` contract: `-i`, `-t`, unparsed words, the command's exit code and `--`.
- `repose cp ./report-*.pdf :tmp/` uses the local glob, and `:PATH` means this checkout's project. No peer CLI has that shortcut.
- While you are attached, ports 1024 and up forward with no command.
- On the machine, typing `apt`, `brew`, `pip` or `crontab` gets an answer that names the repose way (devtools.nix:47-72).

**Asking and answering**
- `repose questions` lists waiting questions across every project. It lists agents at a terminal prompt in a separate group.
- `repose reply` refuses to guess. With two questions waiting it sends nothing and exits 2. It checks the answer against the options (`The answer is one of: yes, no.`), and its success line names who got the answer.
- ntfy shows one button for each option, so you answer from the phone with no command.

**Feedback and safety**
- Progress is one spinner line with the phase and a clock. It turns into `✓ Created todo-app (large)  0.3s`. Build phases count real work: `Fetching 17/42 paths`.
- `repose stop` names the agents it ends: `claude (working) and codex-2 (needs input)`.
- `repose ls --destroyed` shows a RESTORABLE UNTIL date, and `repose restore demo` brings a project back in one command.
- An in-place snapshot restore refuses on a running machine and names both ways forward.
- Every destroy prompt defaults to N, and the temporary-machine prompt says `cannot be restored`.
- One-time notices stay quiet after you have seen them. These are the idle note (idle-noted.json) and the remote note (git_remote.go:82).
- `ls` adds the LEFT and DISK columns only when a row needs them.

**Grammar and scripting**
- `--name`, `--size`, `--temp` and `--multiplexer` print the same help on `run` and `sync`.
- PROJECT is the optional first argument on 27 commands.
- `list` has the alias `ls` in every group. `-q` and `--json` refuse each other with one message, and on an empty list `--json` prints `[]`.
- Success lines share one shape: `Stopped demo in 0.0s with a 1.0 GB snapshot.`
- Progress lines go to stderr, so stdout stays clean for scripts.
- `repose stauts` suggests `status` or `start`. An unknown flag points to that command's own help.
- 27 commands complete project names, and `--agent`, `--size` and `--editor` complete their values.
- `--multiplexer` help states its whole fallback chain. The other defaulted flags can copy that pattern.

## Themes

### 1. You cannot see the agent's work from the laptop

The product exists so that agents work while you are away. On your return, no repose command tells you if the agent committed, on which branch, or what it last printed. You attach and read, or you run `git fetch repose` with no idea if anything is there.

#### 1.1 The machine's git state is hidden, and `stop` drops the easy path to unfetched commits (high)

- **Evidence:**
  - `repose status` prints `host fake-host-01   ip 10.64.4.12   disk 1.0 GB/39.0 GB ...` and `sessions 0   tmux clients 0   docker 0` (status.go:205, 218). It has no branch, no commit count and no uncommitted count.
  - `repose stop` prints `Stopped todo-app in 11s with a 2.1 GB snapshot.` and nothing about commits you have not fetched.
  - The sync no-op line is `Nothing new to sync. The machine has changes your laptop doesn't have (27 files).` (sync.go:1699). It mixes commits with uncommitted files and names no command.
  - The "finished" notification body is the agent's last words.
  - sync.md: "Only commits travel."
  - The one-command workaround today is `repose exec git log --oneline -5`, the Example in exec.go:113.
- **Your experience:** You open the laptop to a "claude finished" email. You want to know if it committed. `status` gives you a host name and a private IP. You run `git fetch repose` blind. If the agent left its work uncommitted, the merge takes nothing, and no message tells you the reason. In the evening you stop machines to free plan memory. The next morning, getting yesterday's commits costs a `repose start` (about 10 s), a fetch and a `repose stop` (11 s or more). `git status -sb` and `gh pr status` show this state at a glance.
- **Proposal:**
  - Add one row to the machine probe that `status` runs. Count against the laptop's `repose/<branch>` ref, never a hardcoded `main`, and give each worktree its own row.
  - Add the same fields to `--json`. This needs a guestd change and an update to `docs/interfaces/` in the same commit.
  - In a checkout, have `stop` fetch before it snapshots. Outside a checkout, print the unfetched count instead. Keep the line about uncommitted files, because it prevents a loss you cannot undo.

  ```
  $ repose status
  checkout  main: 3 commits your laptop has not fetched, 2 files changed
            worktree-1: 5 commits
  $ repose stop
  Fetched main (+3), worktree-1 (+5). Stopped todo-app in 11s with a 2.1 GB snapshot.
  4 uncommitted files on the machine stay in the snapshot.
  $ repose sync
  Nothing new to sync. The machine has 3 commits on main your laptop lacks (`git fetch repose` gets them) and 2 files not committed.
  ```
  Commit counts in the notification body need the hook on the machine to run git. That hook must not log paths (OBSERVABILITY rules).

#### 1.2 You cannot read an agent's recent output without attaching (high)

- **Evidence:**
  - On tmux, `repose ps` shows `WINDOW COMMAND ACTIVE` (ps.go:215-224).
  - `repose logs` defaults to `--kind console`, which holds output only from a failed boot: `todo-app has no console output: repose keeps a machine's console only from a boot that failed.`
  - `repose events` carries hook summaries.
  - No command shows the last lines of an agent's window.
- **Your experience:** To check if an agent is stuck, finished or off track, you attach, press `Ctrl-b w`, pick a window, read it and detach. You repeat that for each window on each project. Docker, fly and kubectl each have a one-shot read: `docker logs NAME`, `fly logs`, `kubectl logs`.
- **Proposal:** Put the read under `ps`, which reads tmux over your SSH connection (I-274). Leave `logs` as it is. Use `tmux capture-pane` over the existing SSH master and never `pipe-pane`. Nothing goes through guestd or the API, so I-49 and the never-log rule hold.
  ```
  repose ps -l                        # adds LAST: each window's last non-empty line
  repose ps todo-app claude-2 -n 20   # that window's last 20 lines
  ```
  The undocumented workaround today: `repose exec todo-app -- tmux capture-pane -p -t todo-app:claude-2 -S -20`.

### 2. Agents are the unit of work, and the commands target machines

You hand work to agents, and agents live in windows. `ps`, `paste` and `questions` name windows. `attach`, `exec` and `run --no-attach` cannot target one or do not report one. You remember window numbers and scan `Ctrl-b w`.

#### 2.1 `attach` cannot open a named window (high)

- **Evidence:**
  - `repose attach` has `--bridge` and `--bridge-allow` and no other flags (cli.go:373-397). `repose paste --window NAME` exists (paste.go:225).
  - `repose questions` prints `claude on todo-app` and drops the window, which the signal carries (questions.go:144-146). The line has no wait time.
  - tutorial-git-workflow.md:79: "`repose attach`, switch to that agent's window".
- **Your experience:** A notification says `claude-2` needs input. You attach and land in `claude`, which is working. You press `Ctrl-b w`, scan the list and pick `claude-2`. You do this several times a day. `tmux attach -t todo-app:claude-2` and `docker attach NAME` each take one command.
- **Proposal:** Reuse the flag `paste` has. Do not add `PROJECT:WINDOW`, because `PROJECT:CHECKOUT` has that meaning (I-480).
  ```
  repose attach todo-app --window claude-2
  repose attach -w 2
  $ repose questions
  Waiting at a prompt in their terminal, which `repose reply` can't answer:
    claude-2 on todo-app   repose attach todo-app --window claude-2
  ```
  On herdr, `--window` means the agent name, as it does for `paste`. Complete the flag from `ps -q`. A wait age needs a `since` field on AgentSignal first.

#### 2.2 Worktree agents are told apart by window order, and `exec` cannot run in a worktree (medium)

- **Evidence:**
  - tutorial-git-workflow.md:36 says windows keep "the same order as the worktrees". Worktree numbers skip any number whose folder or branch is still there (I-342).
  - The tutorial runs tests with `repose exec -- sh -c 'cd ~/todo-app-worktree-1 && npm test'`. `exec` has `-i` and `-t` and no other flags.
- **Your experience:** To review worktree-2 you must remember that its window is `claude-2` and not `codex`. Testing one branch takes a quoted one-liner with a path built from the checkout's folder name.
- **Proposal:** Add a TREE column to tmux `ps` and to `--json`, read from the pane's working directory. Add `--workdir` to `exec`. If `-w` becomes the short form of `run --worktree`, give `--workdir` no short form.
  ```
  WINDOW      COMMAND  TREE        ACTIVE
  1:claude    claude   worktree-1  now
  2:claude-2  claude   worktree-2  4m ago
  $ repose exec --workdir worktree-1 npm test
  ```

#### 2.3 `ps` on tmux shows no agent state (medium)

- **Evidence:** herdr `ps` has a STATE column, and tmux `ps` has ACTIVE in its place. I-274 left state out because it was per agent and a minute stale. The signal now carries the window (I-509), so staleness is the remaining objection.
- **Your experience:** The command for one machine (`ps`) knows less than the summary for every machine (`ls`).
- **Proposal:** Join the signal into tmux `ps` by window. Show `?` when the sample is older than a minute.

#### 2.4 `run --no-attach PROMPT` does not say where the agent went (low)

- **Evidence:** The command prints `Ready in %s.` on stderr and nothing else (run.go:534). PickName chooses the window name (run.go:490), and the name never reaches you.
- **Your experience:** A script that starts three prompts cannot tell which window holds which task. It needs that name for `paste --window` and `attach --window`. `docker run -d` prints the container id.
- **Proposal:** Print the handle on stdout in the tmux target form: `todo-app:claude-2`. A `--json` with project, window, worktree and branch is a further option. Append `(window claude-2)` to the existing `Worktree:` line.

#### 2.5 While you are attached, tmux shows nothing about the other agents (low)

- **Evidence:** The machine's tmux status line is the default plus a clock and the pane title (tmux.nix:129-141).
- **Your experience:** You review `claude` while `claude-2` waits 20 minutes at a permission prompt. Your phone gives the only signal.
- **Proposal:** On each state change, guestd sets an `@repose_state` window option, and `window-status-format` shows one mark. Document the marks in machine.md. The option does not read pane content, so it is compatible with I-49. Make it idempotent, so a guestd restart puts the marks back.

### 3. `status`, `events` and `ls` show the operator's view

The screens you check each day lead with data you cannot act on: a host, a private IP, event enums and run hours that no longer cost anything. They leave out the quantities that refuse a start or add a charge.

#### 3.1 `status` leads with platform internals, and its first line runs together (medium)

- **Evidence:**
  ```
  todo-app   large  running   0m      3 agents: 1 needs_input, 1 working, 1 idle today 0h  month 0h
    host fake-host-01   ip 10.64.4.11   disk 1.0 GB/39.0 GB   snapshot none
    sessions 0   tmux clients 0   docker 0
    last event just now: project.created "project created as large"
  ```
  - The `%-20s` pad on the agents cell lets longer text run into `today` (status.go:296).
  - The sessions line holds the inputs to idle detection.
  - A fork reports `snapshot none`, although it was made from a snapshot.
- **Your experience:** You cannot act on three of the four lines. You parse the one line that matters by position.
- **Proposal:** Use labelled rows in the `fly status` style. Keep host and IP in `--json` and `-v`. That needs a decision entry that amends I-192.
  ```
  todo-app   running 2h14m   large   tmux   agent claude
    agents    claude-2 needs input, claude working, codex idle
    checkout  main: 3 commits your laptop has not fetched, 2 files changed
    attached  nobody
    listening next-server :3000 up 2h 410 MB
    disk      1.0 of 39 GB   snapshot 1m ago
  ```

#### 3.2 `ls` shows run hours that cost nothing and hides plan memory and egress (high)

- **Evidence:**
  - `ls` prints `PROJECT CLASS STATE UP AGENTS TODAY MONTH`, and `status` ends with `today 0h month 0h`.
  - Since I-289, "the month costs the same however many hours run" (billing.md:18). billing.md has a "Seeing your hours" section all the same.
  - `Me.Limits.MemoryGB` exists (api_types.go:32) and nothing shows it.
  - With fake egress at 380 GB, `ls` and `status` printed nothing about it.
  - With billing `past_due`, `ls` looked normal, and the API refused `start`.
- **Your experience:** You learn your budget from a refusal. Before `run --size xl`, `fork` or a second `run`, you cannot see how much of your 8 GB is in use. TODAY and MONTH look like a meter, so you stop machines to save money the plan does not charge.
- **Proposal:** Drop TODAY and MONTH from `ls` and `status`, and update billing.md in the same commit (I-242). Add one account line under the `ls` table. Add warning lines only near a limit that leads to a stop or a charge. Do not add a `plan` noun. The egress figure may need a `/me` field.
  ```
  Solo: 8 of 8 GB running, 41 of 100 GB held, 212 of 250 GB egress this month
  Payment failed Oct 6: running machines stop Oct 9.
  ```

#### 3.3 The idle notification says "still billing" (medium)

- **Evidence:** notify.go:302 sends `todo-app: idle, still billing`. lifecycle.md:65 says an idle machine "costs nothing extra on a plan".
- **Your experience:** The title reads like a running meter. It leaves out the real cost, a blocked start for another machine.
- **Proposal:** Change the title to `todo-app: idle 24h, holding 8 GB of your plan`. Check status.go and the dashboard for the same stale text. Add a decision entry that amends I-262.

#### 3.4 `events` prints UTC, enums and host names, and prints nothing when empty (medium)

- **Evidence:**
  ```
  2026-10-09T01:39:35Z		guest.started	guest started on host-01
  2026-10-09T01:39:35Z	claude	agent_question	Drop the legacy_users table?
  ```
  - `events` formats time with no `.Local()` (logscmd.go:141), and `logs` prints local time.
  - An empty agent column leaves a double tab.
  - `repose events docs-site --since 1s` prints nothing and exits 0.
  - Outside a checkout, `events` exits 4, and `questions` covers every project in the same case.
- **Your experience:** A read of "what happened overnight" needs time-zone math and enum decoding. With two Claude windows you cannot tell the finished one apart. An empty result and a broken command both print nothing, so they look the same.
- **Proposal:** Use local `HH:MM`, a fixed-width table and the verbs that `notify.Title` uses. Keep the raw kinds in `--json`. Cover every project outside a checkout, as `questions` does (I-419). A window column needs a field on Event. Fix `guest ... on host-01` at the producer, because the dashboard shows the same text.
  ```
  20:59  todo-app  claude  finished     Added tests for src/billing.ts; 14 pass
  $ repose events docs-site --since 1h
  No events on docs-site in the last 1h.
  ```

#### 3.5 `logs --kind ops` passes tests against the fake and drops every result against the real API (medium; a bug that shows a pattern)

- **Evidence:**
  - The real handler sends `state`, `duration_ms` and `error`, and no `line` (misc.go:107-125).
  - The CLI decodes `ts`, `kind` and `line` (api_routes.go:369-373), so each production row reads `<ts> start ` with nothing after it.
  - The fake sends `line` (handlers.go:1703-1706).
- **Your experience:** The CLI offers one per-operation history. It lists operations and does not say which one failed. The cause is a pattern: the fake and the real API show you different things.
- **Proposal:** Decode the real fields and print `21:40  start  failed  3.1s  boot_timeout: ...`. Pass the API object through under `--json`. Make the fake send the real shape, and add a test that decodes the real handler's output. Add this to the bug list.

#### 3.6 `run` repeats the same carry lines on every visit (low)

- **Evidence:**
  - `Credentials: gh, codex` prints on every run (run.go:435).
  - `Kept the guest's codex login: it is newer than the laptop's.` and `Not carried (would not work in the guest): git core.pager.` print on every run while the condition holds (carry.go:97-101).
  - The idle and remote notes print once.
- **Your experience:** By the tenth run you skip the block. That habit hides the one new line that matters, for example `Not synced: ...`.
- **Proposal:** Keep a noted file for each project beside idle-noted.json. Print a carry line only when its content changes.

#### 3.7 Without a terminal, progress prints phase starts and never their ends (low)

- **Evidence:** Off a TTY, `Phase` prints `label...` and `End` prints nothing (progress.go:74-78). A piped `run --no-attach` printed two start lines and then 60 s of silence before the error.
- **Your experience:** In a conductor script or CI log, a 60 s hang looks the same as a 2 s step until it fails.
- **Proposal:** On stderr, print `Created todo-app (large) in 0.3s` at the end of each phase, and print `still connecting (30s)` every 30 s on long phases.

#### 3.8 Short ids are cut from different ends (low)

- **Evidence:** `shortRev` takes the first 8 characters of an id (configmenu.go:240-245), and `questions` takes the last 8 (questions.go:92-97). The ids are UUIDv7, so the first 8 hex digits change about every 65 s. Two applies printed `Applied revision 01900000`.
- **Proposal:** Use the random tail everywhere, and accept a suffix wherever an id is taken. This fix overlaps D8.

### 4. The model has more nouns and paths than it needs

Several concepts carry two or three names, and two names carry two meanings each. Parallel work has five mechanisms, each with its own way back and its own clean-up. You have to learn each mapping, and the CLI does not show the machine a command acts on.

#### 4.1 You cannot see which machine a command acts on (high)

- **Evidence:**
  - cli.md:19 gives the order: argument, `--project`, `REPOSE_PROJECT`, git remote.
  - Two more rules live in prose and in the laptop-only file `projects.json`: "uses the machine last made there" (lifecycle.md:153) and the `--on` binding (run-and-attach.md:72).
  - run-and-attach.md:84 tells you to undo `--on` by hand-editing that JSON, and cli.md:397 calls the same directory's caches "safe to delete".
  - `ls` marks no row as this folder's. `ps`, `exec`, `ssh` and `cp` print no project name.
- **Your experience:** After a fork, or with `REPOSE_PROJECT` left over from yesterday, `repose exec npm test` runs on some machine, and the output does not name it. The same `repose run` in `~/scratch` picks different machines on two laptops.
- **Proposal:**
  - Mark this folder's row with `*` in `ls`, as `docker context ls` does.
  - Make `status` name its source: `todo-app (this checkout, by git remote origin)`.
  - On a TTY, give `ps` a header line: `todo-app · running · tmux`.
  - Undo `--on` with `repose run --on PROJECT --forget`, never through `rm`.
  - Print `(REPOSE_PROJECT=todo-app-fork-2)` on stderr for `rm`, `stop`, `restore`, `resize` and `exec`. Print it only when the variable disagrees with the folder's project.

#### 4.2 Five ways to run agents in parallel, each with its own way back (high)

- **Evidence:**

  | Way | Where | Starting point | Comes back with | Clean-up |
  |---|---|---|---|---|
  | second window (`claude-2`) | same tree | live tree | `git fetch repose` | close window |
  | `run --worktree` | same machine | last commit | `git fetch repose` (branch `worktree-N`) | `git worktree remove` + `git branch -D` by hand |
  | `run --name X` | new machine | laptop checkout | hand-typed `git remote add` | `repose rm X` |
  | `fork -n N` | N new machines | snapshot of the disk | hand-typed `git remote add` | `repose rm` each |
  | `run --temp` | new machine | laptop checkout | `git fetch tmp-xxxx.repose:~/app BRANCH` | expiry or last-window exit |

  lifecycle.md:141 recommends `--name` for several agents on one repository, and run-and-attach.md:38 recommends `--worktree` for the same need. `fork` has no `--temp`.
- **Your experience:** Before you try an idea, you pick among five mechanisms. Your pick decides three later things: if `git fetch repose` brings the work back, if you type a remote by hand, and the clean-up steps.
- **Proposal:** Teach two axes in one docs table: *where* (`--worktree` for the same machine, `fork` or `--name` for a separate one) and *how long* (`--temp`, allowed on `fork`). Give one way back that needs no remote. Print it once in the creation output of fork, `--name` and `--temp`, because it prevents lost work:
  ```
  repose fetch todo-app-fork-1 [BRANCH]
  ```
  An opt-in `--remote` on `run` and `fork` can add `repose-<name>` as a remote. Do not write remotes into `.git/config` unless the developer asks.

#### 4.3 "Project" and "machine" mix in help, and `ls` hides lineage (medium)

- **Evidence:**
  - Help lines use both nouns: `rm` "Destroy a project", `stop` "Snapshot and stop a project's machine", `keep` "Keep a temporary machine".
  - After one fork and one `--temp`, `ls` shows four peer rows (`todo-app`, `todo-app-fork-1`, `todo-app-fork-2`, `tmp-pa2n`) with nothing linking them.
  - `run`'s Long text says "environment" (cli.go:314).
- **Your experience:** "A project's machine" suggests that a project can exist without a machine, and it cannot. You rebuild lineage from the names.
- **Proposal:** Keep "project" as the noun (CLAUDE.md fixes it). Use it alone in the help Short lines: `Snapshot and stop a project`, `Keep a temporary project`. Change "environment" to "machine". Add a FROM column to `ls` that shows a fork's parent and the origin repository of `--name` and `--temp` copies.

#### 4.4 "Idle" means two things, and agent states have three vocabularies (medium)

- **Evidence:**

  | Surface | Waiting | Done |
  |---|---|---|
  | `repose ls` | `needs_input` | `idle` |
  | `repose stop` | `needs input` | (not named) |
  | `repose events` | `needs_input` | `completed` |
  | ntfy and email title | `needs input` | `finished` |
  | notifications.md:66 | "`repose ls` shows `needs input`" | |
  | `repose ps` (tmux) | (none) | (none) |

  `ls` prints `claude: idle` for an agent at its prompt, and `todo-app: running for 26h with nobody attached` for an "idle machine". `idle.go:37` prints that line even when an agent sits at `needs_input`.
- **Your experience:** An email says todo-app is idle while `ls` shows `claude: working` on it. You grep scripts for two spellings. A machine whose agent has waited a day for you reads as unused.
- **Proposal:**
  - In all text output, print `working`, `idle` and `needs input`. Keep snake_case in `--json`, and do not invent `finished` as a state.
  - Call the machine state `unused for 26h`.
  - When an agent waits at a prompt, write `api: claude-2 has waited at a prompt for 26h`.

## The daily-flow table

Times come from the docs or from runs against the fake API. RT means a network round trip.

| # | Task | You type today | You must remember | Round trips and waits | Friction (theme) |

### What keeps each grade below A

- **Mental model.** `stop` fetches and `status` counts only from the `repose` remote. Thus a project you reach through a named remote (`todo-app-fork-3`) gets no fetch. `--temp` work comes back only through a URL that you type. `fork` has no `--temp`. `run -w -p` types into an agent, and `rm PROJECT:CHECKOUT` removes a checkout. `ssh` and `code` do not start a stopped machine. `ls` shows no lineage for `run NAME` or `--temp` copies.
- **First hour.** The quickstart says that agents do not survive a stop. I-636 makes them reopen. `repose run prj`, with a project called `proj`, created a second large machine without a question. From a folder that is not a repository, `run` creates a project, and the plan question then offers to stop a real machine. The quickstart has a separate `repose login` step and a step 3 that asks for no action.
- **Daily flow.** To answer a Claude Code permission prompt you type a 6-word `run` command, and that command also copies logins. `questions` starts with "No questions are waiting" and then lists agents that wait. After a fetch, `status` reports work that you did not merge as "nothing new". The `-w` flags do not complete window names. No stop and start on a real machine has shown that agents resume.
- **Consistency.** On 10 commands PROJECT is only a flag, and two of them read the words wrong without an error. In some places the CLI finds what you meant and refuses. Short flags, metavars, the place of the empty-list line, the exit code for a missing item and `--json` coverage still differ.
- **Feedback.** `run -w W -p TEXT` confirms nothing, and off a terminal it exits 1 after it typed the text. stdout from `run` and `sync` has a progress line, so a script cannot read the window name alone. A failed boot does not point to the console in `logs`. Time formats, check marks and window names still differ in small ways.
- **Discoverability.** Tab completion offers file names where the CLI knows the valid words (`config add`, `open`). `deploy` suggests `reply`. `push`, `kill` and `update` get no suggestion. Root help does not show how you get work back. Some empty outputs give no information.
- **Peer conventions.** There is no login without a browser. gh, fly, vercel and railway read a token from an environment variable. `whoami` and `auth` point to `repose login`, not to `login --status`. `open` refuses PROJECT as its first word, and its error shows that it knew what you meant. `events` has no `-n`. `top` suggests `stop`.
- **Confidence.** `rm` can lose agent work for good, but it does no fetch and no git probe. `stop` does both. When the probe before a stop cannot reach the machine, the stop line says nothing, and that looks the same as "nothing left behind".

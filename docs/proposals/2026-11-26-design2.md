# Proposal: design 2 on the Mac, challenged and measured

**Status:** proposal for the owner's judgment. Docs only; no product code.
d2-arch, design 2 program (`~/briefs/design2-program-2026-11-26.md`),
2026-11-26. Every number below was measured on the program's Mac (AWS
mac-m4.metal, Apple M4, 10 cores, 24 GiB, macOS 15.8.3 24H241) unless a
row says otherwise. The UX measures of today's design (D1) and of the shape
proposed here are d2-lab's (`docs/reports/2026-11-26-design2-ux.md`); this
document gives the architecture, the challenges and the build plan.
Prototype sources and raw logs: `/mnt/nixstore/sharing/d2-arch/` (`s/`
scripts and the `vzx2` and `krx` launchers, `go/` the Go probes, `*.log`
the runs).

## Headline

- **No Linux VM on the Mac.** hostd runs on macOS; each machine is its own
  Virtualization.framework VM in its own launchd job; the network is user
  space (6 Gbit/s at MTU 1500 to the Mac, the internet at the Mac's own
  rate, where D1 gets 0.78-0.79 Gbit/s down of the Mac's 1.05-1.11), volumes are APFS files (a snapshot is a 26 ms
  clone). One hostd codebase stays, with a second substrate.
- **The park works on VZ.** The spike's "save kills the guest" was the
  missing login session: VZ encrypts each save file with a Secure Enclave
  key. With an unlocked session, 10 of 10 saves restored with memory kept, at 1-3 s a
  machine. It needs the user's session unlocked to restore, and never runs
  as root.
- **A restart still loses memory unless repose starts it.** macOS quits the
  VZ service with the session at the first signal, on the Apple-menu path
  and at `shutdown -r`; an app holding the logout does not save it. A park
  repose starts before the restart kept two machines' memory.
- **Memory while running: VZ never gives it back; libkrun does** (3.9 to
  1.1 GB in 5 s by free page reporting), but libkrun has no save, so no
  park. Recommendation: VZ, with idle machines resting by park (1.2 s save,
  0.55 s restore, all memory returned), and libkrun as a later second runtime.
- **After a power loss with nobody logged in**, running machines come back
  cold (as D1's do) and parked ones wait for the login (section 2.9).
- **Cost: 32-39 builder days** (section 5).

## 1. The shape I recommend

**hostd runs natively on macOS. Each machine is its own
Virtualization.framework (VZ) VM, run by a small per-machine launcher that
is its own launchd job in the user's login session. There is no Linux
appliance.** Volumes are sparse files on APFS; snapshots and forks are APFS
clones. The network is user space inside hostd: each VM's NIC is a VZ
file-handle attachment to hostd's switch, which ends in gVisor's netstack
(the egress rules become Go code at the place every connection is dialled)
and, for the edge, in wireguard-go on the same netstack. The park is VZ's
own save and restore, whose file the Secure Enclave already encrypts.

One hostd codebase stays: the guest manager already reaches the substrate
only through interfaces (`internal/hostd/guest/manager.go` `Deps`:
`lvm.LVM`, `systemd.Systemd`, `ch.Client`, `hnet.Net`, `vsockclient.Dialer`,
`mount.Mounter`). The Linux implementations stay exactly as they are for the
fleet and for x86 owned hosts; a darwin build adds a second implementation
of each. That is the whole split.

Call this **D2n** (native). The alternative kept to the end, **D2b** (VZ
guests beside a small Linux appliance that keeps hostd, nftables and
WireGuard), is measured below and loses on every number and on the
"one hostd" argument it was meant to win (section 3.2).

### What it gives a user, against today

| One build, H / P at 4 vCPU | 62-119 s / 35-151 s (spike, nested) | 42-55 s / 27-37 s (spike, VZ) |

## 2. The assumptions, and what each challenge showed

Each heading is an assumption the brief named or one the evidence raised.
"Measured" means on this Mac today with the log named; "read" means from
source or Apple's documentation, cited; anything else says unmeasured.

### 2.1 "VZ save/restore kills a repose guest" (the spike, 3 of 3): false

The spike's three failures were not a device. I reproduced them (4 of 4
killed: the spike's device set, without the entropy device, and with only
the read-only root disk and NAT, no rng, balloon, vsock or serial;
`park.log`), then read the VZ XPC service's own log at the moment of the
save: `SecKeyCreateRandomKey ... CryptoTokenKit SEPClientObject: createKey`,
then `SecKeyCreateRandomKey_ios failed: -25308 errKCInteractionNotAllowed`,
then the service dies with `EXC_BREAKPOINT`
(`/Library/Logs/DiagnosticReports/com.apple.Virtualization.VirtualMachine-2026-11-26-114245.ips`,
copied to `crash-min.ips`). VZ encrypts every save file with a key the
Secure Enclave holds for the logged-in user. Apple says the same in words:
"These files are hardware encrypted ... No other Mac or user account can
read another's save file, or restore the virtual machine" (WWDC23 session
10007, "Create seamless experiences with Virtualization"). The spike, like
every EC2 Mac, ran with no GUI login, so the key could not be made.

With autologin on (a generated password in a 0600 file on the Mac, never
printed; conductor 11:44Z), measured:

| Run | Device set | Save | Restore in a new process | Memory kept |
|---|---|---|---|---|
| n=1 | ro root + NAT | 3.27 s, 1.21 GB | 2.15 s | yes (boot_id and a 1 GiB fill's sha256) |
| n=3 | the spike's full set (rng, balloon, vsock, serial, ro, NAT) | 2.59-2.99 s, 1.24 GB | 1.33-1.37 s | 3 of 3 |
| n=1 | + a virtiofs share | 2.60 s | 1.36 s | yes |
| n=1 | + the share **mounted, a file held open**, written after restore | 1.18 s, 111 MB (idle) | 0.55 s | yes; the write reached the Mac |
| n=1 | 8 GiB, 4.4 GB touched | 8.57 s, 4.36 GB | 5.14 s | yes |

So no device breaks it, including the shared directory tart refuses to
suspend with (tart `Sources/tart/Commands/Run.swift`, commit 8e9d61d). The
save file is the memory the guest has touched, written at about 0.5 GB/s
and read back at about 0.85 GB/s.

Two rules came with it, both measured:

1. **The session must be unlocked to restore.** At 12:25Z the display had
   slept and the screen locked (`CGSSessionScreenIsLocked=Yes`); every
   restore then failed `VZErrorDomain Code=12 "permission denied"` (n=5)
   with `SecKeyCreateDecryptedDataWithParameters failed -25308 ...
   unable to compute shared secret`. Saves succeed while locked (encryption
   needs only the public key). After two restarts the session came up
   locked at once (the lab Mac's loginwindow carried
   `autoLoginUserScreenLocked = 1`, which I did not set: macOS's or the
   AMI's) and restores failed the same way; with it set to 0, the screen
   lock off and display sleep off, every restore after that worked. The
   rule is inferred from these two states, locked and unlocked, every time
   the same; Apple does not document it.
2. **It must run as the user, in the user's session.** As root (sudo) the
   save kills the VM, as it does with no session (n=1). A LaunchDaemon with
   `UserName` set to the user, which is how D1's appliance runs
   (`/Library/LaunchDaemons/run.repose.appliance.plist`), boots a VZ VM but
   cannot park it: its save killed the VM, and a restore of a state saved in
   the session failed "The virtual machine failed to start", both with a
   console session present (`hd.sh`, `hd.log`, 2026-11-26 14:51Z). Only a
   LaunchAgent in `gui/<uid>` can park.

macOS 26 was not needed and was not tried.

### 2.2 "A Mac restart keeps the machines' memory" (I-1386): the save is not the limit; the shutdown window is

Measured: two machines parked (6.96 s for both), then `sudo shutdown -r
now`, then autologin, then both launchd jobs restored at boot: 13.5 s each
in parallel on a cold disk at load 14, ssh 15.3 and 16.1 s after the jobs
started, boot_id and fill hash unchanged (`rb.sh`, `rb.log`). That proves
save, restart and restore at login.

It does not prove that a restart gives the time to save. D1 measured that
`sudo shutdown -r now` gives the launcher about one second
(`docs/features/own-hardware.md`, I-1434, ENG-138), and the promise is
withdrawn from the docs for that reason. Measured for D2 (`rs.sh`, `rs.log`):
two machines, each its own launchd job whose launcher pauses and saves on
SIGTERM, through both restart paths:

| Restart | SIGTERM reached the job | The VM at that moment | Saved | Memory after login |
|---|---|---|---|---|
| Apple menu path (`tell application "System Events" to restart`, 14:14:58Z) | 4.4 s later, both jobs | already `stopped unexpectedly` (rs1) or in state `error` 4 ms into the park (rs2) | no | lost, both (cold boot by the jobs) |
| `sudo shutdown -r now` (d2-lab, 14:17:15Z) | the same second | state `error` 4-10 ms into the park | no | lost, both |

macOS ends the VZ XPC service of every VM in the session at the same
moment it signals the session's agents, so no `ExitTimeOut` and no
SIGTERM handler gets a VM saved. D2 does not fix the restart case by
itself; it has the same window D1 has, which is none.

Holding the logout does not help either, measured: a faceless
`NSApplication` LaunchAgent (`s/parkapp.swift`, registered with
LaunchServices) received `applicationShouldTerminate` 3.9 s after an
Apple-menu restart (14:46:15.035Z), answered `.terminateLater` and told
both launchers to park; rs1 paused at .053 and began its save, and at .229
its VM "stopped unexpectedly"; rs2 got SIGTERM at .224. The VZ XPC service
checks in with LaunchServices as an application of its own (its launch log
reads `"ApplicationType"="UIElement"`), so the logout quits it with every
other app, whoever holds the logout. Any design whose VMs live in the user's
session has this limit, D1's vfkit included.

What works, measured (`rb.sh`): **a park repose starts before the
restart.** Two machines parked in 6.96 s, the Mac restarted, both restored
at login with their memory. So the restart promise becomes: a restart
started through repose (`repose host restart`, or the dashboard; a macOS
update scheduled through repose) keeps every machine's work; a restart from
the Apple menu, a software update that macOS runs on its own, a power cut or
a panic does not. That is more than D1 has today, which is a clean launcher
stop only.

Two things D2 changes at a restart all the same. A machine resting by park
(section 2.5) is already a file, so a restart costs it nothing. And a
machine that does lose its memory is back in seconds: D1's machines
answered ssh 51-65 s after the Mac's boot at d2-lab's restart (14:18Z),
against D2's 13.5 s to restore two parked machines and 1-2.5 s to boot one
cold.

### 2.3 "We need a repose Linux VM on the Mac": no

What the appliance does today and where each part goes in D2n:

| The appliance's job | In D2n | Evidence |
|---|---|---|
| Run hostd (Linux) | hostd built for darwin/arm64 | the substrate seam above; Go cross-builds; cgo only in the launcher |
| Run Cloud Hypervisor guests nested | each guest is a VZ VM | spike: one layer fewer, every build 1.2-2x faster, pairs up to 12x |
| LVM thin pool | APFS sparse files, `clonefile` | section 2.6 |
| nftables + tc (egress rules, policer) | Go, in the netstack's dial and in the switch | section 2.4 |
| wg0 to the edge | wireguard-go on gVisor netstack | section 2.4 |
| systemd units (`guest@`) | one launchd job per machine | section 2.7 |
| The park key over vsock 1386 | not needed: VZ encrypts the save | section 2.1 |
| Memory isolation of guests (`guests.slice`) | each VM is its own macOS process; macOS's compressor and its jetsam | spike: macOS compresses an idle VM |

Keeping a small appliance only for the network (D2b) was measured and is
worse (section 3.2).

### 2.4 "The network needs Linux (nftables, WireGuard)": no, and user space is faster here

Measured with `d2perf` (a Go TCP probe in the guest and on the Mac; 10 s
streams n=3, 2000 request/response, 200 connects; `net.log`), guest 2 vCPU:

| Path | Stream, Gbit/s | RR p50 / p99, us | Connect p50, us | Internet, 100 MB |
|---|---|---|---|---|
| (a) VZ NAT straight to the Mac (no rules: not a candidate) | 108-111 | 57 / 72 | 148 | 0.74 Gbit/s |
| (b) **D2n:** file-handle NIC, gvproxy v0.9.0 (gVisor netstack), MTU 1500 | 5.98-5.99 (4 streams 6.10) | 70 / 88 | 182 | 1.32 Gbit/s |
| (b) same, MTU 65520 | 36.4-38.0 (4 streams 41.4) | 80 / 101 | 191 | 1.27 Gbit/s |
| (c) **D2b:** file-handle NIC, `d2sw` VLAN switch, router VM (nft masquerade), VZ NAT; guest to router hop, MTU 1500 / 9000 / 65000 | 2.4 / 11.3 / 26.3-27.2 | 120-134 | - | - |
| (c) D2b full path to the Mac, any MTU | 2.20-2.25 | 141-145 / 170-187 | 361-369 | 0.35-1.17 Gbit/s |
| (d) libkrun guest (unixgram with TSO offloads, `krun_add_net_unixgram`) to gvproxy, MTU 1500 | 19.2-20.8 | 97 / 128 | 256 | - |

VZ's file-handle attachment carries plain frames (MTU 1500 to 65535, Apple:
`VZFileHandleNetworkDeviceAttachment.maximumTransmissionUnit`), so at 1500
every segment crosses user space; libkrun's unixgram backend negotiates
TSO and checksum offload, which is why (d) is three times (b) at the same
MTU. Raising the MTU on the guest's NIC gives VZ most of that back.

The Mac itself downloads the same file at 1.15 Gbit/s, so every candidate
reaches the internet at line rate; the internet column is noise from one
public server. Port 25 is closed even on plain VZ NAT here (AWS blocks it),
so the smtp rule could not be observed on this Mac.

What the rules become in Go, read from `images/appliance-arm64/host/etc/repose/nftables.nft`
and `internal/hostd/net/net.go`:

- guest-to-guest isolation (`br-guests` bridge rules): each guest's NIC is
  its own port on hostd's switch and its own netstack NIC; nothing forwards
  between them unless hostd writes it.
- private destinations (`nftables.nft:131-132`: the owner's LAN, the mesh,
  link-local), smtp (I-238), stratum (I-239), flow rate (I-240): checks in
  the TCP/UDP forwarder before hostd dials out on the guest's behalf; each is
  a counter with the same `reason` label. The hook exists: gvisor-tap-vsock's
  forwarder already refuses link-local (EC2 metadata) per connection before
  it dials (`pkg/services/forwarder/tcp.go:36-39`, f54d9ec, 2026-11-26).
- the upload policer and download shaper (`tc` in net.go:288-334): a token
  bucket per guest on the switch port.
- the edge (DESIGN §7): wireguard-go with `tun/netstack` holds the host's
  WireGuard key; the gateway's `10.64.x.y:22` arrives as a netstack
  connection and hostd splices it to the guest's port 22. Measured cost of a
  wireguard-go netstack tunnel on this M4 (both ends user space, so a lower
  bound): 1.05 Gbit/s, request/response p50 49 us, p99 87 us (`d2wg`, 5 s,
  `krnet.log`). The edge path is the user's internet link, so this is not
  the limit; it is CPU, about two cores at that rate.

gvisor-tap-vsock (Apache-2.0, the library behind gvproxy, which Podman
ships with vfkit and krunkit) already does the NAT, DHCP, DNS and port
forwarding; hostd would embed it and add the rule hooks. Its unixgram
protocol is the one VZ's file-handle attachment and vfkit speak
(`VFKT` first datagram, vfkit `pkg/vf/virtionet.go:90`).

Rejected: macOS 26's `VZVmnetNetworkDeviceAttachment` (custom vmnet
networks; WWDC26 session 224) isolates by network membership but has no
egress filter, so the rules would still need pf (root) or user space;
a Network Extension needs signing and the user's approval; plain VZ NAT
puts every VM on one subnet with the user's LAN reachable and no per-VM
rule.

### 2.5 "VZ is the hypervisor": yes for now; libkrun is the memory answer and lacks the park

Hypervisor.framework through libkrun 1.19.8 (Homebrew bottle, installed on
the lab Mac; launcher `s/krx.c`, 50 lines) boots the **unchanged** repose
guest bundle: ssh in 0.99-2.1 s. Its virtio-balloon offers free page
reporting (guest `features` bits 1, 3, 5 and 32: stats, free page hint,
reporting, version 1), which VZ's balloon does not (spike: bits 0, 2, 29,
32, 34). Measured (`mem.log`), 4 GiB VM, 3 GiB touched in the guest and
freed:

| | footprint after the free | 5 s later | 60 s later |
|---|---|---|---|
| libkrun, `KRUN_FREE_PAGE_REPORTING_MODE_REPLACE` | 3 889 MB | 1 111 MB | 1 112 MB |
| libkrun, default mode (madvise) | 3 905 MB | 3 906 MB | 3 907 MB |
| VZ (the spike's device set) | 3 661 MB | 3 661 MB | 3 661 MB |
| VZ, guest `init_on_free=1` | 4 104 MB, resident from boot (cause not traced; the kernel zeroing pages it frees at boot would do it) | 4 104 MB | 4 104 MB |
| VZ, then a 21 GiB incompressible hog on macOS (swap to 11.3 GB) | 3 664 MB | 3 664 MB through the hog | 3 664 MB after it |

`phys_footprint` counts a process's compressed and swapped pages too, so the
VZ rows say the guest's freed memory was never given back, not where macOS
kept it; the spike saw macOS swap an idle appliance's RSS to 254 MB with its
footprint unchanged. Under VZ the freed pages are charged to the Mac until
the VM stops, and macOS may page them out, paying a fault when the guest
touches them (2 GiB re-touched in 1.0 s after the hog, 0.6 s without).

libkrun's header says why the default does nothing on macOS: "madvise()
doesn't release guest memory that the guest has written to"; Replace mode
remaps reported 2 MiB blocks (`include/libkrun.h`, v1.19.8, 2026-11-04;
`src/devices/src/virtio/balloon/macos.rs`). That is I-1626's "unused memory
goes back to it", which no VZ configuration gives.

What libkrun lacks, read from its 1.19.8 C API (`krun_*` list in the
header): no save/restore and no pause. So libkrun today means no park, no
resting and no launcher upgrade without a reboot of every machine. QEMU
with HVF was neither run nor read here; it would be the largest of the three
to ship and keep, and nothing measured above calls for it.

VZ's answer to memory is a different one, and it is measured: **rest an idle
machine by parking it.** An idle 4 GiB machine saves in 1.18 s to a 111 MB
file and its process exits, giving every byte back to macOS; it restores in
0.55 s (section 2.1). That is resting (I-818) that returns memory, which CH's
`vm.pause` never did. Its limit is the unlock rule: a machine parked while
the user is away cannot be woken by an ssh from a laptop if the Mac's screen
has locked. So hostd rests by park only when the session is unlocked or the
user has chosen no screen lock, and otherwise rests by VZ `pause` (2-4 ms,
memory kept).

Woken by an ssh, measured (`wake.sh`, `wake.log`, n=3): the machine parked
(1.86-1.93 s, a 0.67-0.69 GB file, its launchd job not running), an ssh
arrived at a small proxy standing in for hostd's switch (`go/wakeproxy`),
which kickstarted the job; the job's wrapper restored the state and the
proxy spliced the connection to the guest's sshd through gvproxy.
`ssh ... true`-style commands answered in 5.8-8.7 s with the memory kept,
against 0.06 s to a running machine through the same proxy. The VZ restore
is about 1.1 s of that; the rest is the guest's network coming back through
a new gvproxy, which exits when its VM's socket closes. hostd's own switch
keeps the port across a park, which should remove most of it (not
measured).

The choice the owner has to make is in section 4. My recommendation:
**VZ as the runtime**, behind the same `ch.Client`-shaped interface, because
it alone keeps the park, resting and launcher upgrades without a reboot of
the machines; **libkrun kept as a measured second runtime** (memory back
while running, no park) that the same launcher protocol can carry later.

**The park's time follows the configured memory, not only the touched
memory** (found by d2-runtime on e2e-d2n, 15:31Z; measured here, `memsz.sh`,
`memsz.log`, same guest, same 1 GiB fill, state files 1.24-1.34 GB):

| Configured | 4 GiB | 6 GiB | 8 GiB | 12 GiB | 19.5 GiB (I-1640's host figure) |
|---|---|---|---|---|---|
| Save, s | 2.55-2.64 | 3.09 | 3.64 | 4.74 | 6.65-6.83 |
| Restore, s | 1.33-1.66 | 1.53 | 9.55 | 9.84 | 11.67-11.69 |

So I-1626's "every guest boots with the host's placeable memory" costs
about 10 s on every unpark and every wake from rest under VZ, and under VZ
a large configured size also buys nothing back, since nothing returns while
the VM runs. On D2n each guest gets a configured memory, 6 GiB by default
(the largest measured below the step; the spike's three builds ran in 6 GiB
VMs), with the host's figure as a ceiling the user can choose; this amends
I-1626 for D2n only and wants its own decision when built.

### 2.6 "LVM thin volumes": APFS files are as good or better

Measured (`apfs.sh`, `apfs.log`): a running machine's 8 GiB volume with
2.2 GB written, frozen by the guest (`fsfreeze`, 1.5 s window), cloned with
`cp -c` (APFS `clonefile`) in **26 ms**; free space unchanged by the clone
(128.26 GB before writing, 126.09 after writing 2.17 GB and cloning); 500
MB written in the original afterwards cost 512 MB; the clone booted as its
own machine with the frozen file and its hash intact. New volumes: 17-27 ms
for a 40 GB sparse clone (spike).

| LVM operation (`lvm.LVM`) | APFS equivalent |
|---|---|
| CreateVolume, ExtendVolume | `ftruncate` a sparse file (grow at stop only: VZ has no live disk resize; I-1660 already grows the filesystem at the next start) |
| Snapshot, Clone | `clonefile` |
| Mkfs | no mke2fs on macOS: the guest's initramfs makes the ext4 on an empty vdb (a guest change) or hostd ships mke2fs |
| VolumeStats, PoolStats | allocated blocks of the file; `statfs` of the APFS volume |
| RemoveVolume | `unlink` |

What is lost: a live grow of a running machine's disk (CH `vm.resize-disk`,
I-66); it takes effect at the next start. A full APFS volume behaves as a
full thin pool does: writes in the guest fail (unmeasured).

### 2.7 "VMs die with their owning process": true, so give each its own

Measured (`life.sh`, `life.log`): `kill -9` of the launcher ends the VM at
once (its XPC service exits with it, n=2). A VM run by its own launchd job
in `gui/<uid>` survived the ssh session that made it and answered from a new
one; `launchctl bootout` of the job ends it. A **launcher upgrade by park**
(pause, save in the old job, bootout, bootstrap a job that restores) left a
3.37 s gap (save and exit 2.18 s, restore to ssh 1.19 s) with the same
boot_id.

So: hostd is one launchd job, each machine another. A hostd update or crash
touches no machine; hostd reconciles at start from `launchctl list` (the
`guest@*` units' job today, CLAUDE.md "reconciles"). A launcher update
parks and restores each machine in about 3 s, or waits for its next stop.
Parkable VMs must run in the user's session (2.1), so their jobs are
agent jobs in `gui/<uid>`; hostd itself is a root LaunchDaemon (the
appliance's launcher is a LaunchDaemon today,
`/Library/LaunchDaemons/run.repose.appliance.plist`), so it runs before a
login (section 2.9).

### 2.8 "hostd stays one codebase for Mac and x86": yes, with a second substrate

The interfaces in 2.3 are the seam; the guest manager (11 168 lines in
`internal/hostd/guest`) does not change shape. New darwin code, by
interface: `lvm.LVM` (19 methods) on files; `systemd.Systemd` (7) on
launchd; `ch.Client` (6, plus snapshot and restore for the park) on the
launcher's control socket; `hnet.Net` (14) on the switch and netstack;
`vsockclient.Dialer` unchanged if the launcher answers Cloud Hypervisor's
hybrid-vsock handshake (`CONNECT <port>`) on a unix socket, as it can
through `VZVirtioSocketDevice.connect(toPort:)`; `mount.Mounter` unused.
Host figures (`MemInfo`, `Load1`, the cgroup readers) come from
`host_statistics64` and the per-VM process's `task_info`. The fleet's
Linux build is untouched.

### 2.9 "Machines come back after a power loss with nobody logged in": only if they are not parkable, so hostd runs two kinds of job

D1's appliance is a LaunchDaemon with `UserName` (it runs at system start,
before anyone logs in). Measured for D2 (`hl.sh`, `hl.log`), three restarts
with `sudo shutdown -r now`:

| Boot | Logged in | LaunchDaemon VZ machine (`UserName` = the user) | LaunchAgent VZ machine (parked before the first boot) |
|---|---|---|---|
| autologin off, n=2 | nobody; no `gui/501` domain | started at system start (session 0), ssh and internet answered | did not run; its park file waited |
| autologin on, n=1 | the user, at boot | started cold again, before the login | restored at login in 8.1 s (cold disk), memory kept across all three restarts |

And from 2.1: the daemon kind cannot park (its save kills the VM and it
cannot restore a park, even with a session present); the agent kind cannot
run before a login. So no single job kind gives both "comes back with
nobody logged in" and "keeps its memory".

What hostd does, and what the user sees:

- A machine is started as an **agent job** whenever a session exists
  (every start the user makes while logged in, which is nearly all of
  them): it parks, rests by park, survives a restart through repose.
- At system start with **nobody logged in** (a power cut on a desk Mac
  without autologin), hostd, itself a LaunchDaemon, starts the machines that
  were running and have **no park file** as **daemon jobs**: they come back
  cold, as D1's do today (D1: 51-65 s; here a boot is 1-2.5 s), and run
  without a park until their next stop. Their status says
  `running (no park until restarted)`; a rest falls back to pause.
- Machines **with a park file** wait for the login, because only a session
  can restore them. Their status says `parked, waiting for you to log in to
  <host>`; the 6-hour rule (I-653) runs from the park, and past it hostd
  starts them cold as daemon jobs and says so.
- At the first login, nothing running is interrupted: daemon-kind machines
  keep running until their next stop, and become agent jobs at their next
  start.

Settled by d2-runtime (15:46Z, `ldt.sh` on the lab Mac): a LaunchDaemon
with `UserName` can bootstrap a job into `gui/<uid>` but not into
`system`; a root LaunchDaemon can do both, and a `system` job it makes with
`UserName` runs as the user. So hostd on D2n is a root LaunchDaemon, as
hostd on Linux runs as root, and it never runs a VM as root (a VM saved as
root dies, 2.1): each VM is an agent job in `gui/<uid>` while the user's
session exists, else a `system` job with `UserName`.

Built and measured on the skeleton by d2-runtime (16:23-16:29Z, e2e-d2n
through production): with autologin off, hostd as a root LaunchDaemon came
up and reached the api through the edge with nobody logged in; the two
parked machines were held, records and images untouched; the unparked one
started as a `system` job running as the user (ready in 5.5 s, exec through
the edge, a new boot_id) once a `launchctl print gui/501` exit 125 ("Domain
does not support specified action", no session) was read as "no job there".
At the next boot with autologin on, hostd saw the session 16 s after boot and
restored both parked machines by 19 s after boot, one with the same boot_id
and fill hash across both restarts; the third came back as an agent job.

This is one more piece of hostd's darwin substrate (the launchd jobs know
two domains, `system` with `UserName` and `gui/<uid>`), about one day,
added to item 3 below.

### 2.10 The first end-to-end journey on the skeleton (design2 a4e25773, 16:00Z)

On e2e-d2n through production, as a customer's CLI does it, project e2e-j1
from a real checkout (`s/j.sh`, `j1.log`): `repose run -d` 11.9 s ("Ready in
12s"); `repose exec` through the edge 1.02-1.08 s; `ps`, `status` fine;
`stop` 1.1 s; `start` 6.8 s with the disk kept; snapshot, a later write,
stop, `snapshots restore -y` 8.8-9.1 s with the later write gone and the
earlier file back. A **hostd restart failed it**: after
`launchctl kickstart -k gui/501/run.repose.hostd` every `exec` answered
"environment is not accepting connections yet" for minutes, the VMs alive.
hostd's log: "parked machines wait for this Mac's login session to be
unlocked", `locked=true`. The new hostd held its whole start behind the
unlock wait because one park record existed, and the screen had locked by
itself about 25 minutes after an unlocked autologin, with the screen lock
off and display sleep off.

Two rules follow, for the build and for every Mac: **hostd never holds a
running machine for the session**; only a parked machine's restore waits,
per machine, retried at unlock, its image kept, never discarded for a lock.
And **an unlocked session is never assumed**: the restore of a parked
machine, a wake from rest by park, and a launcher upgrade by park all need
it, so each must fail safe (keep the file, say "waiting for you to unlock
<host>") rather than fall back to a cold boot.

Part of the same failure was the network, found by d2-runtime (16:11Z):
VZ drops a file-handle attachment whose peer went away (the guest's eth0
logs "Lost carrier" at a hostd restart and never gets it back, even after
the launcher reconnects the same socket), so the launcher has to make a new
socket and set a new attachment on the running VM's network device, which
VZ allows. With that, and port sockets owned by the user under a root
hostd, a hostd restart under a running machine cost `exec` 1.20 s with the
same boot_id.

**The journey again on design2 f9d660b6** (d2-runtime-2 and d2-net merged;
16:39-17:05Z, project e2e-j2, `j2.log`, `j2hr.log`, hostd's own log for the
rest): create 12.0 s; exec through the production edge 1.0-1.1 s; stop
0.95 s; start 6.4 s; snapshot restore 9.2 s, correct; **a hostd restart
under the running machine: exec 2.4 s later, same boot_id**; rest by save
after 15 minutes idle (save 1.8 s, a 220 MB image, the VM process gone), a
wake by an exec through the edge (restore 0.88 s, wake 1.0 s); **`repose
host restart -y`: "Parked 3 machines in 5.4s; restarting this Mac.", the
three restored in 10.7 s after the boot, exec answering 55 s after the
command, all three with the same boot_ids.** Attach was not timed here.
Left open by the skeleton: the api shows a parked machine waiting for a
login as "not answering"; the CLI's ssh ControlMaster (`ControlPersist`)
keeps a machine from resting for its span after the customer's last
command; the 6-hour rule for held parks; a product install.

## 3. The two shapes that were measured and not chosen

### 3.1 D1, today

D1 stays where it is until D2n ships, and on x86. Its costs on the Mac are
measured by the lab and the spike: the nesting (builds 1.2-2x slower alone,
pairs 3.7-15x), the appliance's 12.3 GB held from boot, and a park whose key
is not hardware-backed and whose restart window does not exist.

### 3.2 D2b, VZ guests beside a small appliance

It keeps nftables and wg0 unchanged, which was its point. Measured: the
guest's path through a userspace switch and the appliance's forwarding is
2.2 Gbit/s at any MTU and 141-145 us request/response, against D2n's 6.0
Gbit/s and 70 us at MTU 1500. It still needs every darwin piece of D2n
except the network (VMs must be launched on macOS in the user's session by
a macOS process, volumes must be files macOS can attach, the park is VZ's),
so it does not keep one hostd: hostd in the appliance would drive a macOS
agent over vsock for runtime, volumes and samples, a second control plane.
And the appliance costs memory and a boot of its own on every Mac restart
(not measured here; today's is 12 GiB, a router needs well under 1).

## 6. What this did not settle

- A software update that macOS installs on its own schedule: not run on
  purpose. The lab Mac is offered macOS 27.2.1 (a major upgrade, "Action:
  restart"); installing it would change the OS under d2-lab's baseline, and
  `AutomaticallyInstallMacOSUpdates` is 0 on this AMI. Its restart goes
  through the same logout as the Apple-menu restart, which ended every VZ
  VM at once, so by that measurement an update macOS runs alone loses the
  machines' memory. The answer is a repose-driven update: park every
  machine, then `softwareupdate --install --restart` (not tried).
- hostd's own switch keeping a parked machine's port, so a wake by ssh is
  closer to the 1.1 s restore than the 5.8-8.7 s measured with gvproxy.
- VZ memory under pressure measured by RSS: only `phys_footprint` was read.
- libkrun's virtio-fs, vsock and console with repose's guestd: only boot,
  ssh, the balloon and the network were tried.
- d2-lab's UX numbers for D1 and for D2n end to end through repose (create,
  attach, agent start, ports, the browser) do not exist for D2n: nothing of
  D2n is built into repose. Every D2n figure here is the prototype's.
- macOS 26 was not tried; nothing here needed it.
- One Mac, one macOS version, AWS's hardware; no customer's Mac with
  FileVault, a real display or a sleep schedule.
- QEMU with HVF: neither run nor read.
- The egress rules in Go, the edge over wireguard-go and the launcher's
  vsock bridge are designs; only their transports were measured.

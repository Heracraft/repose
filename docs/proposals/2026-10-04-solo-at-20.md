# Solo at $20 (proposal, 2026-10-04)

**Status: proposal. Nothing here is decided.** A price change needs a
`DECISIONS.md` entry, a change to `docs/PRICING.md` and a change to
`internal/billing/plans.go` (PRICING.md, "Changing prices"). This document
records one research session with the owner on 2026-10-04.

## The question

The owner asked: can the introductory price of Solo go down to $20 a
month, with unit economics that make some sense? Later in the session the
owner added two facts:

- Another path is to use credits until a cloud company (AWS, Azure or
  Vercel) acquires repose.
- The Microsoft for Startups offer is $25,000 at its current milestone.
  The owner is also applying for $10,000 from AWS.

## Summary

1. On the current Azure host, Solo loses money at $20 and also at $29.
   This is true when a user keeps one `large` running all month.
2. While credits pay for the hosts, the price has almost no effect on the
   burn. The host costs the same amount when its seats pay $20 or $29.
3. A permanent $20 price needs cheaper memory. Bare metal or a
   memory-optimized cloud instance gives this.
4. Suspend when idle is the largest lever. On prod, a running `large` was
   fully idle in 84% of its running minutes.
5. Recommendation: launch Solo at $20 for the first three months, then
   $29. Put the next engineering work into suspend when idle. Choose hosts
   by price per GB of memory.

## Measured usage on prod

Source: `meter_samples` and `usage_hours` on the production database,
2026-09-20 to 2026-10-04. One sample is one minute of one running
machine. Most of this traffic is from the owner and from tests. It does
not show how paying users behave.

| Class | Running minutes | Projects | Host RSS p50 | Host RSS p90 | Average cores | p95 cores | Attached | Agent working | Fully idle |
|---|---|---|---|---|---|---|---|---|---|
| `large` | 51,074 | 89 | 5.60 GB | 8.05 GB | 0.047 | 0.230 | 11.4% | 3.7% | 84.1% |
| `small` | 24,254 | 36 | 1.10 GB | 1.14 GB | 0.004 | 0.009 | 1.5% | 0.0% | 98.5% |

"Fully idle" means: no SSH session, no tmux client, no agent in the
`working` state, and less than 0.15 cores of CPU in that minute.

Other facts from the same data:

- Fleet egress was 28 GB in total in 14 days.
- The average allocated disk was 34 GB for each project-hour.
- On host-01, the 5 live guest volumes allocate 180 GB and use 94 GB.
- On days with normal work, the fleet ran 70 to 127 machine-hours a day,
  which is 18 to 38 GB of memory on average.
- The `small` row is mostly one idle test machine (`m3-iso-c`).

Conclusions:

- A running `large` uses its full 8 GB of host memory at p90. The guest
  page cache fills it. Without a balloon or reclaim, this memory does not
  go back to the host.
- CPU is not the limit. A host can give 4 vCPU to each `large` with 4:1
  oversubscription or more.
- Most running time is idle time. A machine that sleeps when idle needs
  memory only for the time that it works.

The query for the table:

```sql
with s0 as (
  select project_id, ts, class, mem_rss/1073741824.0 gb,
         cpu_ns - lag(cpu_ns) over w as dcpu,
         extract(epoch from ts - lag(ts) over w) dt,
         tmux_clients, ssh_sessions, agents
  from meter_samples where state = 'running'
  window w as (partition by project_id order by ts)),
s as (select *, case when dt between 30 and 90 and dcpu >= 0
                     then dcpu/1e9/dt end cores from s0)
select class, count(*) mins, count(distinct project_id) projs,
  percentile_cont(0.5) within group (order by gb) rss_p50,
  percentile_cont(0.9) within group (order by gb) rss_p90,
  avg(cores) avg_cores,
  percentile_cont(0.95) within group (order by cores) p95_cores,
  avg((tmux_clients > 0 or ssh_sessions > 0)::int) attached,
  avg((agents::text like '%working%')::int) agent_working,
  avg((not (tmux_clients > 0 or ssh_sessions > 0)
       and agents::text not like '%working%'
       and coalesce(cores, 0) < 0.15)::int) idle_all
from s group by class;
```

## What the code does for memory today

- cloud-hypervisor starts each guest with `--memory size=N,shared=on`
  (`internal/hostd/ch/ch.go:95`).
- There is no balloon, no free page reporting and no KSM. On host-01,
  `/sys/kernel/mm/ksm/run` is 0.
- The guest has zram swap (`nix/guest/base/sysctl.nix`).
- hostd counts each guest as its class memory plus 512 MiB.
- R1-5 says that a guest stays on until `stop`. There is no idle
  auto-stop and no code for it.

## The levers

### 1. Suspend when idle

This is the largest lever. On prod, 84% of the running minutes of a
`large` were fully idle. An idle machine can save its memory to local
NVMe and continue when a user connects or an agent starts work. Then one
8 GB seat can serve about three users.

What it needs:

- A decision that supersedes R1-5.
- The plan text changes from "running at once" to "working at once".
- A memory snapshot and restore path in hostd. cloud-hypervisor v52 (about
  June 2026) added on-demand restore with userfaultfd and sparse memory
  snapshots.
- A rule for "idle": no agent is working and no one is connected
  (`proposals/2026-09-27-flat-plans.md` has the same rule).
- Headroom for peaks: many users work at the same hours.

Published resume times: Blaxel about 25 ms, CodeSandbox 0.5 to 2 s.

### 2. Memory density without suspend

Running guests use their full memory at p90. These three methods give
memory back to the host:

- KSM: 8 similar Debian guests went from 13.15 GB to 6.77 GB, a 48.5% cut
  (credativ, 2025). NixOS guests from one base share more pages.
- Free page reporting: cloud-hypervisor supports
  `--balloon size=,deflate_on_oom=on,free_page_reporting=on`. It returns
  free guest pages. It does not return the page cache.
- zswap: Meta's TMO saved 20 to 32% of memory across its fleet.

The expected gain is 1.3 to 1.5x. The risk is a host OOM that stops
tenant machines. Placement needs a headroom rule before memory is
oversubscribed.

### 3. Hosts with cheaper memory

- Bare metal in the US: Latitude 512 GB at $650 ($1.27 a GB), Hivelocity
  1 TB at $750 ($0.73 a GB). Both are AMD.
- A memory-optimized cloud instance: AWS R and Azure E families give 8 GB
  for each vCPU. The `D64s_v7` gives 4 GB for each vCPU. Repose needs
  memory more than CPU, so an R or E host costs about half for each seat.
- Before the launch host is ordered, examine if East US has an Ev7 size.
  I-39 recorded that v5 and v6 sizes are not available in this
  subscription in East US.

### 4. Egress allowance while hosts are on Azure

250 GB at Azure's $0.087 a GB is $21.75. This is more than the plan
price. Prod used 28 GB in 14 days across all users. An introductory tier
with 100 GB of egress costs a typical user nothing. It sets the worst
case at $8.70. Hetzner and Latitude include their traffic.

## Three ways to sell $20

**A. $20 for the first three months, then $29.** Paddle Billing does this
with a recurring discount: `recur: true` and
`maximum_recurring_intervals: 3`. With a trial, the discount starts when
the trial ends. Each customer costs $27 of revenue, which is acquisition
cost. No code changes. This is the recommendation.

**B. $20 for life for the first 100 subscribers.** The flat-plans
proposal had this at $15. It costs nothing in cash while credits pay. If
hosts are still on Azure when the credits end, it gives 100 seats that
lose money each month.

**C. $20 as the list price.** Only after lever 3, and lever 1 or 2.

Churn at this price: median monthly customer churn is 6.1% for ARPA under
$25 (ChartMogul). At 6%, a customer stays about 16 months, and lifetime
revenue at $20 is about $300. Card-required trials convert at about 31 to
49% (secondary sources).

## The credits path

The owner named a second path: use credits until a cloud company buys
repose. On this path, the price has little effect. One `D64s_v7` costs
about $3,090 a month for 30 seats. 30 seats at $20 instead of $29 is $270
a month less revenue. That is about 9% of the burn.

The limit on this path is the seat count. 30 users is a small number to
show a buyer. Thus the useful work on this path is also density: suspend
when idle and memory-optimized hosts. They give more users for each
credit dollar.

The owner is applying for $10,000.

X8i, I7i and their variants. There is no extra cost. These are Intel, so

## Code work for a host on AWS

Projects are pinned to a host (R2-3). A host on AWS needs:

1. **Snapshots in S3.** `internal/hostd/snapshot/blob.go` defines a
   `Blob` interface. S3 is a second implementation with IAM instance-role
   authentication. The Azure managed-identity code needs an AWS
   equivalent.
2. **An OpenTofu AWS host module.** It makes a VPC, the instance, a gp3
   or io2 data volume for the thin pool, and the role. R3-20 already plans
   a second host module.
3. **WireGuard to the edge.** Hosts connect to the api through WireGuard
   (I-92). An AWS host is one more peer on the public internet. AWS
   us-east-1 and Azure East US are both in Virginia, with a few
   milliseconds between them.
4. **Egress.** The Solo allowance problem is the same on both clouds.

A host on a second cloud also gives the host-loss drill and the
cross-host restore. Both are still open.

## Recommendation

1. Launch Solo at $20 for three months, then $29 (option A). Set the
   introductory egress at 100 GB.
2. Choose hosts by price for each GB of memory. On AWS, use an R
   instance. On Azure, use an E size if East US has one. This halves the
   burn compared with the `D64s_v7` plan.
3. Build suspend when idle next. It helps on both paths: on credits it
   gives about 3x the users for each host, and off credits it makes $20
   profitable.
4. Start the Azure 60-day workload count now. Add services only if
   repose keeps them after the credits.
5. Price a Latitude 512 GB server as the host that comes after the
   credits.

## Decisions for the owner

1. Option A, B or C for the $20 price.
2. Supersede R1-5 and build suspend when idle.
3. Which Azure services to add for the workload milestones, and how much
   R3-4 lock-in to accept.
4. A host on AWS. This needs the S3 `Blob`, the AWS host module, and
   entries that amend R2-3 and R3-20.
5. A memory-optimized launch host (E or R) in place of the `D64s_v7`
   (amends I-39).

# Webhooks into a project's machine (proposal, 2026-11-10)

**Status: proposal; nothing here is decided.** A Stripe, GitHub, Clerk
or Twilio integration needs a public HTTPS URL that the provider can
POST to. Today a repose machine has no public path, and the docs send
the user to `cloudflared` (`apps/web/src/content/docs/machine.md:172-175`).
This proposal gives each project named webhook routes on one public
hostname. Each route has its own unguessable token and forwards to a
port and path inside the machine. The edge forwards body bytes and
signature headers unchanged, so the app's own provider checks pass. A
frozen machine wakes and gets the delivery. A stopped machine answers
503, and each route can say whether a delivery may start it. The
product value council put this at Ports item 5 and "Later"
(`reports/2026-11-04-product-value-council.md:117,232`) and called it
"the only public path" worth adding. The owner calls it key.

The design keeps three rules as they are: guests get no new inbound
port (the edge reaches the app through the guest's sshd, as `repose
open` does), the edge stores no request, and no tenant secret gets a
new home. It becomes real only through the `DECISIONS.md` entries in
section 8, which amend R2-6, I-257, I-479, I-818/I-822, I-1063 and I-10.

Provider facts were checked on 2026-11-10 in the providers' own docs
and carry their URL in "Sources". Facts the docs did not state are
marked *unverified*.

## Summary

| Question | Answer |
|---|---|
| URL | `https://hooks.repose.herakraft.co/<project_id>/<route>/<token>[/rest][?query]`. One hostname, routed by path |
| Why a path and not a subdomain per project | One certificate from TLS-ALPN-01 on the edge's own :443, one DNS record, no Cloudflare token. A wildcard needs DNS-01 and the token that has blocked the preview certificate since 2026-09-20 |
| How the edge reaches the app | The gateway's own SSH connection to the guest's sshd, and a `direct-tcpip` channel to `127.0.0.1:<port>`. No change to the host's nftables; the app may listen on localhost only |
| Where routes live | In the api, set with the CLI and the dashboard. This follows I-820's reasons for `keep_awake` |
| CLI | `repose webhooks` (add, rm, rotate, url, and a list). The name `hooks` is taken by agent hooks |
| Wrong token | 404 from the edge's in-memory table. No api call, no wake, no dial |
| Frozen machine | Wake (`vm.resume` takes 9 to 10 ms, I-818), then deliver |
| Stopped machine | 503 with `Retry-After`. A route with `--start` also starts the machine once per 10 minutes |
| Destroyed project, deleted or rotated route | 410 for 30 days, then 404 |
| Store-and-forward | Not proposed. Most signature checks reject a delivery older than 5 minutes, so a stored body is useless when it arrives late |
| `Repose-Signature` | Not in the first version. An HMAC key on the edge would be a new home for a secret; an Ed25519 platform key is the compliant shape if the owner wants it |
| Limits | Request body 1 MiB; reply body 64 KiB, JSON, XML, form or plain text only; 10 requests a second per route, 30 per project, 8 at a time per project |
| Egress | Request bytes are ingress and free. The edge counts reply bytes per project and adds them to egress, because I-1063's meter cannot see them |
| Logging | Route id, status, outcome, duration and byte counts. Never the path (it holds the token), the query, a header or the body |
| Abuse | No HTML, no redirects, no cookies, small replies and unguessable URLs. A route can answer a provider; it cannot serve a page |
| Size | About 12 to 15 engineering days in four stages (section 9), *estimate* |

## 1. The repo today

**The edge and its :443.** The edge VM runs the SSH gateway on :22, the
WireGuard hub, and "the preview-proxy stub on :443 (a static page until
the feature exists)" (`nix/edge/default.nix:1-11`). The gateway unit
gets `PREVIEW_LISTEN = ":443"` with `PREVIEW_TLS_CERT` and
`PREVIEW_TLS_KEY` under `/var/lib/repose/edge/tls/`
(`nix/edge/default.nix:382-384`), and `cmd/gateway/serve.go:130-135`
opens that listener only when the certificate loads (`tlsListener`,
`serve.go:193`, DECISIONS I-479). The wildcard certificate was never
issued: issuing one needs the Cloudflare API token
(`docs/workstreams/06-gateway-edge.md:403-405`), and STATUS on
2026-10-04 says "preview listener still lacks its wildcard certificate
(since 2026-09-20)". The edge's nftables accept 443 from anywhere with
no per-source cap (`nix/edge/default.nix:279`), while 22 has a
connection cap and a rate per source (`:274-277`, I-435).

**The preview stub.** `internal/gateway/preview/preview.go` parses
`<port>-<name>.repose.herakraft.co` (`:36-54`), keeps the label opaque
because a slug and a handle joined by a dash cannot be split back
(I-438), returns `ErrNotImplemented` from `Authenticate` (`:58-60`), and
serves a static 503 page (`:73-95`).

**How the gateway reaches a guest.** Only by SSH. The host forwards
from `wg0` to the guest bridge on tcp 22 and nothing else
(`nix/hosts/nftables.nix:252`). `session.dialGuest`
(`internal/gateway/relay.go:192-260`) gets a 5-minute gateway
certificate for the project (`POST /internal/gateway-certs`,
`docs/interfaces/api.md:392`), wakes a frozen machine first, and dials
`guest_ip:22`. Clients may open `session` and `direct-tcpip` channels
(`relay.go:68`). `repose open PORT` is a `direct-tcpip` channel to
`127.0.0.1:<port>` or `::1:<port>` through that relay
(`docs/features/ports-and-previews.md:73-77`).

**Wake.** The route from `GET /internal/route?login=` carries
`resting` (`internal/gateway/api.go:58-72`). `Gateway.wake`
(`relay.go:784-803`) calls `POST /internal/wake` with the reason
hard-coded to `"connect"` (`relay.go:789`). The api answers within
`WakeTimeout = 8 * time.Second` (`internal/api/resting/resting.go:91`).
The route cache holds an answer for 5 s (`internal/gateway/cache.go:24`).

**The rest rule.** A project with an open `gateway_sessions` row cannot
rest (`resting.go:247`), and a sample taken while resting is never
quiet (`resting.go:223`). So a woken machine stays awake for at least
15 quiet minutes before it rests again.

**The word "hook" is taken.** `cmd/repose-hook` is the guest binary
behind `repose-notify` and `repose-ask`. The gateway's `HookIngest`
serves `POST /hooks` on the WireGuard address for agent hook events
(`internal/gateway/hookingest.go:34-38`), with a 4 KB body cap and 10
requests a second per guest (`:20-23`). The public docs say "as its
hooks report it" for agent states (`apps/web/src/content/docs/agents.md:84`).
Claude Code's `settings.json` has its own `hooks` key.

**Egress.** I-1063 (branch `run-sync-fixes`, 2026-11-10) bills only what
a guest sends out of the host's uplink, counted by nft in the new
`guest_meter` chain. Traffic from the guest to the edge is not counted.
Its "Not done" list says preview responses "must count" and that
`guest_meter` would gain a rule for a preview port. That plan assumed
previews dial the guest's port directly; a reply that rides the
guest's port 22 looks the same as a terminal's output to nft.

**Dashboard cookies.** The sign-in cookie is host-only (no `Domain`),
`Path=/callback`, `HttpOnly`, `Secure`, `SameSite=Lax`
(`apps/web/src/routes/signin/+server.ts:51-63`). The DNS names are
`repose.herakraft.co`, `api.repose.herakraft.co` and
`ssh.repose.herakraft.co` (`infra/dns/main.tf:8-11`); Logto is
`accounts.herakraft.co`. All are the same site as any
`*.repose.herakraft.co` name.

**Per-project settings.** I-820 put `keep_awake` in a column on
`projects`, a `PATCH /projects/:id` field and a dashboard switch, and
rejected a `config.toml` key ("per-project server-side state, not a
laptop preference") and a `repose.nix` option ("the api would have to
parse an evaluated guest configuration") (`docs/DECISIONS.md:25151-25165`).

**Platform files in the guest's secrets tmpfs.** I-10 already writes
three reserved names (sshd keys) into `/run/repose/secrets/`, and the
api refuses those names on `PUT /secrets`.

## 2. What the providers do

From the providers' docs (URLs in "Sources"):

| Provider | Timeout | Retries | Auto-disable | Signature covers | Notes |
|---|---|---|---|---|---|
| Stripe | not documented | Live: up to 3 days, exponential. Sandbox: 3 tries in a few hours | Yes, after "several days" | `t.rawbody` (`Stripe-Signature`) | 3xx is a failure. Libraries reject a timestamp older than 5 minutes by default |
| GitHub | 10 s | **None.** Redelivery is by hand or through the REST API | not for failures | raw body (`X-Hub-Signature-256`) | 25 MB payload maximum |
| Svix (Clerk, Resend) | 30 s | at once, 5 s, 5 min, 30 min, 2 h, 5 h, 10 h, 10 h (about 32 h) | Yes, after 5 days of failures | `id.timestamp.body` (`svix-*`) | 3xx is a failure. A receiver can answer `webhook-delivery: disable` |
| Twilio | connect 5 s, total 15 s | 1 retry, on a TCP or TLS failure only, by default | No | **the full URL** (scheme, host, path, query) plus POST params (`X-Twilio-Signature`) | No published source IPs |
| Slack Events | 3 s | 3 retries in about 6 minutes | Yes, at 95 percent failures in 60 minutes | `v0:ts:rawbody` | Rejects a timestamp older than 5 minutes |
| Shopify | 1 s connect, 5 s total | 8 in 4 h | Yes, subscription removed after the 8 | raw body | |
| Linear | 5 s | after 1 min, 1 h, 6 h | "might be disabled" | raw body | |
| Polar | 10 s | 10, exponential | Yes, after 10 failures in a row | Standard Webhooks | repose's own billing provider |
| Discord interactions | 3 s to answer | not documented | Removes an endpoint that accepts bad signatures | timestamp + raw body (Ed25519) | The reply body is the interaction's answer |
| Telegram | not documented | "give up after a reasonable amount of attempts" | not documented | no signature; optional secret-token header | Ports 443, 80, 88, 8443 only |

Four facts from this table shape the design:

1. **Body bytes must arrive unchanged** for every provider that signs.
   Host and path may change for all of them except Twilio, which signs
   the full public URL.
2. **The reply body matters** for Slack's `url_verification` challenge,
   Discord interactions and Twilio's TwiML. The edge must pass it back.
3. **3xx is a failure** at Stripe, Svix and Polar. The edge must never
   redirect, and it should not pass an app's redirect through.
4. **Retry windows differ by a factor of 1,000.** Stripe retries for 3
   days; Slack for 6 minutes; GitHub not at all. No provider documents
   honouring `Retry-After`, and only the Standard Webhooks spec says a
   sender "should" disable an endpoint on 410 (*unverified* for each
   provider).

## 3. The design

### 3.1 URL: one hostname, routed by path

`https://hooks.repose.herakraft.co/<project_id>/<route>/<token>`, where
`project_id` is the project's UUIDv7, `route` is the name the user
chose (`[a-z0-9-]{1,32}`), and `token` is 22 characters of base64url
(128 random bits). Anything after the token is appended to the target
path, and the query string is passed as it came.

A subdomain per project (`<name>.hooks.repose.herakraft.co`) was
weighed against the code:

| | Path on one name | Subdomain per project |
|---|---|---|
| Certificate | One name. Go's `autocert` gets it with TLS-ALPN-01 on the :443 the gateway already holds | A wildcard needs DNS-01 and the Cloudflare token that does not exist. Per-name certificates hit Let's Encrypt's 50 per registered domain per 7 days, and `herakraft.co` is shared with the dashboard |
| DNS | One A record, by hand while `manage_dns` is false (`infra/README.md` "DNS while manage_dns is false") | A wildcard record |
| Name | Path segments split cleanly, so I-438's dash problem does not arise | Needs a per-project label the api keeps unique (I-438) |
| Origin isolation between tenants | None, and none needed: section 3.5 lets no reply carry HTML, script or cookies | One origin per project, which matters only if replies were pages |
| Survives a handle change or a reused slug | Yes, the id is stable | Only with a new label scheme |

The path form wins on every row that applies to a webhook. Origin
isolation is the subdomain's one real gain, and it protects browsers,
which a webhook route does not serve.

The project id makes the URL long (about 110 characters). Providers
take it; Stripe's endpoint URL field has no documented limit below
that (*unverified*). A slug and handle would read better, but a handle
can change and a destroyed project's slug can be used again, and a URL
pasted into a provider's dashboard must outlive both.

**Hostname.** `hooks.repose.herakraft.co` works now. R4-12 says repose
is hosted under `herakraft.co` "until it graduates to its own domain",
and webhook URLs live in third parties' dashboards, so whichever name
ships must answer forever. A separate registrable domain (for example
`repose-hooks.net`) would also take tenant replies off the site that
holds the dashboard and Logto. Section 3.5 already closes the cookie
and script risks, so this is a question of permanence and reputation.
It is decision 2.

**No Cloudflare proxy.** A proxied record would add DDoS protection but
Cloudflare would terminate TLS and see every body, which the privacy
policy would then have to name. The record is DNS only, as `ssh.` is.

### 3.2 Where routes live, and the CLI

**Where.** In the api: a `webhook_routes` table, `/projects/:id/webhooks`
routes, a dashboard section and a CLI noun. I-820's reasoning applies
in full. A route is per-project server state; the edge must know it
whether or not a laptop is open; and the api would otherwise have to
read a file from the checkout, which it never does.

A `[webhooks]` table in a repo file (`repose.toml`, which does not
exist, or `repose.nix`) was the starting idea. It has one strength:
the route travels with the code that serves it. It loses on three
counts. The token cannot live in the repo, so the file holds only half
the route. The api would learn of a change only when some laptop runs
`repose run` or `sync`, so two laptops with different branches would
flip the routes back and forth. And I-820 rejected `repose.nix` for a
simpler setting for this same reason. A `config.toml` key fails the
same way: it is a laptop preference file.

**CLI.** The owner's rule is to fold a command under an existing noun
first (`cli-surface-taste`). The candidates:

| Placement | Why not |
|---|---|
| `repose open --webhook` | `open` is a foreground forward that dies with the CLI. A route is lasting server state |
| `repose config webhooks ...` | `config` is the Nix environment; `config add stripe` already means a menu entry or a nixpkgs attribute |
| `repose secrets ...` | The user never types the token in; repose mints it |
| `repose hooks` | Agent hooks own the word: `repose-hook`, `/hooks` on the edge, Claude Code's `hooks` key, `agents.md` |
| `repose webhooks` | Recommended. One new noun, with verbs the CLI already uses (`add`/`rm` as in `config`, `list` as in `secrets`) |

The preview, as it would print:

```
$ repose webhooks add stripe 3000/api/webhooks/stripe
https://hooks.repose.herakraft.co/0193a5e2-7c41-7d0e-9b8a-2f6c1d4e5a90/stripe/Xq3k9LmZpR2vT8wYb1nC4d

$ repose webhooks add github 3000/api/webhooks/github --start
https://hooks.repose.herakraft.co/0193a5e2-7c41-7d0e-9b8a-2f6c1d4e5a90/github/H7tQ0sWfKe5mUa2yLp9rJx

$ repose webhooks
NAME     TARGET                      START  LAST DELIVERY  STATUS
stripe   :3000/api/webhooks/stripe   off    2 min ago      200
github   :3000/api/webhooks/github   on     1 h ago        503 stopped
twilio   :4000/sms                   off    never

$ repose webhooks url stripe
https://hooks.repose.herakraft.co/0193a5e2-7c41-7d0e-9b8a-2f6c1d4e5a90/stripe/Xq3k9LmZpR2vT8wYb1nC4d

$ repose webhooks rotate stripe
https://hooks.repose.herakraft.co/0193a5e2-7c41-7d0e-9b8a-2f6c1d4e5a90/stripe/b8Nf2QeVr6GhK0zTw4mYsA

$ repose webhooks rm twilio
```

- `add NAME PORT[/PATH]` creates a route, or changes the target and
  `--start` of an existing one and keeps its token. The output is the
  URL and nothing else, so `| pbcopy` works.
- `--start` and `--no-start` set whether a delivery may start a stopped
  machine (section 3.6). Default off.
- `rotate NAME` replaces the token at once. The old URL answers 410.
  For a change with no gap, the docs show `add stripe-2` with the same
  target, paste the new URL into the provider, then `rm stripe`. Two
  routes may share a target, so no grace window is needed.
- `list` is also `ls` and the bare noun. `--json` prints every field,
  URL included; `-q` prints names.
- `repose status` gains one line: `webhooks: stripe 200 2 min ago,
  github 503 1 h ago`.
- Exit codes are the existing ones: 2 for a bad name or target, 1 for a
  refusal from the api.

The dashboard's project page gets a Webhooks section with the same
table, a copy button per URL, Rotate, Remove and the Start switch.

**In the guest.** An agent that sets up Stripe needs the URL to call
Stripe's API or to write it in a README. The api sends the route list
with the secrets, as a reserved name in the secrets tmpfs:
`/run/repose/secrets/repose-webhooks` holds one line per route,
`NAME URL`. It travels in `WriteSecrets`, so `rotate` reaches a running
guest within seconds, as a secret does. The guest agent guide gains
one line naming the file. This needs I-10 amended (a fourth reserved
name), which is decision 12.

### 3.3 Tokens and the three homes

- The api mints the token and stores it twice: `sha256(token)` for
  lookups, and the token itself as ciphertext under the account's data
  key, with the same envelope as named secrets (`docs/features/secrets.md`
  "ciphertext in Postgres"), so `repose webhooks url` can print it
  again.
- The edge receives only `(route_id, project_id, name, port, path,
  allow_start, sha256(token))`. A copy of the edge's memory gives no
  working URL.
- The guest receives the URL in its secrets tmpfs (3.2).

So the token lives as ciphertext in Postgres and as a file on the
guest's tmpfs: the two homes CLAUDE.md names for secrets. Nothing new
holds it in plain text.

A token that once existed and was rotated or deleted stays in a
`webhook_tombstones` table as its hash, with the time, for 30 days. The
edge answers 410 for it, and 404 for a token it never saw.

### 3.4 What the edge forwards

**Request, edge to app:**

- Method, as sent. All methods pass: Meta and Strava verify an endpoint
  with a GET, and Twilio can be set to GET.
- Path: the route's target path, then anything after the token. The
  query string unchanged.
- Body: the bytes as they came, streamed, never decoded or
  re-encoded. `Content-Encoding` and `Content-Length` pass unchanged.
- Headers: all of them, in order, duplicates kept, except:
  - hop-by-hop headers (`Connection`, `Keep-Alive`, `TE`, `Trailer`,
    `Transfer-Encoding`, `Upgrade`, `Proxy-*`), which HTTP requires a
    proxy to drop (RFC 9110 §7.6.1);
  - `Host`, set to `localhost:<port>`. This departs from "all headers
    unchanged" on purpose. Vite answers only `localhost`, `.localhost`
    and IP addresses by default (`server.allowedHosts`), so a Vite dev
    server would refuse `hooks.repose.herakraft.co`. No provider in
    section 2 signs `Host` except Twilio, which signs the whole URL and
    is covered below;
  - any `Repose-*` header the sender set, which the edge removes before
    it adds its own.
- Added: `X-Forwarded-For` (the sender's address), `X-Forwarded-Proto:
  https`, `X-Forwarded-Host: hooks.repose.herakraft.co`,
  `Repose-Webhook: <route name>`, `Repose-Delivery: <uuid>`, and
  `Repose-Webhook-URL: <the full public URL with query>`.

**Twilio.** Its helpers take the URL to check as an argument
(`validateRequest(authToken, signature, url, params)`). The app passes
`Repose-Webhook-URL`. The webhooks docs page shows this in Node and
Python. That header holds the token; it reaches only the app, inside
the user's own machine.

**Reply, app to provider:**

- Status passed through, except 3xx, which becomes 502 with no
  `Location`. Providers count 3xx as a failure in any case, and a
  passed redirect would make the hostname an open redirect.
- Body passed through only when its `Content-Type` is
  `application/json`, `text/plain`, `application/xml`, `text/xml` or
  `application/x-www-form-urlencoded`, and only up to 64 KiB. Any other
  type has its body dropped and gets `Repose-Body-Dropped: type`; a
  longer body is cut and the connection closed. Slack's challenge,
  Discord's answers and TwiML all fit.
- `Set-Cookie` removed. `Content-Security-Policy: sandbox;
  default-src 'none'`, `X-Content-Type-Options: nosniff` and
  `Cache-Control: no-store` added.
- Timeout: 30 s from the last body byte to the first reply byte, which
  is Svix's figure and above every other documented one.

### 3.5 Why the reply rules matter

A webhook route is a public URL whose reply a tenant controls. Without
the rules in 3.4, a tenant could return an HTML login page under a
`herakraft.co` name, set a cookie with `Domain=.repose.herakraft.co`
that the dashboard would then receive, or redirect visitors from a
repose URL to anywhere. With them, a reply is at most 64 KiB of JSON,
XML, form data or plain text that a browser may not run, frame or
cache, with no cookie and no redirect. That is enough for every
provider in section 2 and too little for a page.

### 3.6 Machine states

The edge reads the project's state from `GET /internal/route`, extended
to take `project_id=` (it takes `login=` today), with the same 5 s
cache.

| State | Answer | Notes |
|---|---|---|
| `running` | Deliver | |
| `running`, frozen (`resting`) | Wake, then deliver | `POST /internal/wake` with a new reason `webhook`. `vm.resume` is 9 to 10 ms (I-818); with the api round trip and an SSH handshake the target is under 1 s, inside Slack's and Discord's 3 s (to be measured, section 10). The I-822 retry (wake and dial again after a failed dial) applies as it does to SSH |
| `stopped`, route `--start` off | 503, `Retry-After: 3600` | Body: `repose: the machine is stopped` |
| `stopped`, route `--start` on | 503, `Retry-After: 60`, and the api starts the machine | At most one delivery-started start per project per 10 minutes. The start counts against plan memory as any start does; a refusal is recorded as the outcome `start_refused` and the edge still answers 503. An event `webhook_start` names the route in `repose events` |
| `creating`, `building`, `starting`, `stopping`, `restoring` | 503, `Retry-After: 30` | |
| `error`, or the host unreachable | 503, `Retry-After: 300` | |
| `destroyed`, route deleted, token rotated | 410 for 30 days, then 404 | The project's routes are deleted with it. `repose restore` does not bring them back; new tokens mean new URLs, and a sender that obeyed the 410 has already let go of the old ones |

**Why the start is not held open.** A start takes about 12 to 14 s,
longer than GitHub's 10 s and Twilio's 15 s total and far beyond
Slack's 3 s. A held request would fail at those providers anyway and
tie up an edge connection. The 503 tells the provider to retry, and
the retry finds the machine running.

**Why `--start` defaults off.** `repose stop` is a deliberate act that
frees plan memory. A route that undoes it on every delivery would
surprise a user who stopped a machine to start another on a full plan.
The cost of off: GitHub never retries, so a stopped machine loses its
GitHub deliveries until the user redelivers; Slack, Shopify and Polar
may disable the endpoint after a few hours of 503s. The webhooks docs
page names those three and GitHub in one table, so the user can turn
`--start` on for them. This is decision 6.

**After a delivery.** A delivery is not a gateway session: the edge
does not post to `/internal/sessions`, so it never holds a machine
awake past the 24 h `SessionWindow` (`resting.go`). A woken machine
still stays up 15 minutes, because the samples taken while it rested
are not quiet (`resting.go:223`). A provider that delivers every few
minutes keeps the machine awake, which is work the user asked for.

### 3.7 Store-and-forward: evaluated, not proposed

Storing a request at the edge while the machine is stopped, then
delivering it at the next start, would save GitHub's deliveries. It
fails on four counts:

1. **Signatures expire.** Stripe's libraries reject a timestamp more
   than 5 minutes old by default; Slack's docs say to ignore one older
   than five minutes; Svix leaves the tolerance to the receiver, and its
   libraries use 5 minutes (*unverified* in Svix's docs). A body stored
   for an hour arrives with a signature the app refuses. Only GitHub and
   Linear's header signatures carry no timestamp.
2. **Tenant data at rest in a new place.** A Clerk `user.created` holds
   names and emails; a Stripe event holds customer details. A queue on
   the edge holds exactly what CLAUDE.md's logging rule says never to
   keep, and the privacy policy would have to say so.
3. **Secrets.** A payload can carry a token (an OAuth app's
   installation event, a CI provider's job token). A stored body is
   then a fourth home for a secret.
4. **The providers already store.** Stripe holds a failed event for 3
   days, Svix for about 32 hours, Polar for 10 retries. A second queue
   at repose duplicates theirs for every provider except GitHub.

The one compliant shape found: the edge seals each body to a
per-project X25519 public key whose private half lives only on the
guest's disk, keeps the sealed box for at most 24 hours, and a guest
service replays it to the app on start. The edge cannot read what it
holds. It still fails point 1, so it would help GitHub alone, and
GitHub's own "Redeliver" button does the same thing. Not worth an L
size of work.

### 3.8 `Repose-Signature`: evaluated, not in the first version

The starting design had the edge sign each delivery with an HMAC under
a per-project secret, delivered to the guest as a named secret.

- The edge would need that secret in plain text to sign. The api would
  send it to the edge, and the edge would hold it in memory: a third
  holder of a tenant-scoped secret, which "Secrets have three homes"
  forbids.
- What it would prove is that the request passed the edge's token
  check. Inside the guest, the only other callers of `127.0.0.1:3000`
  are the user's own processes. The provider's signature still has to
  be checked, because the token proves only that the sender knew the
  URL.

If the owner wants it, the compliant shape is asymmetric: the edge
signs `delivery id, timestamp, route, sha256(body)` with one Ed25519
platform key, held on the edge as its TLS and SSH host keys are, and
the guest checks it with the public key at `/etc/repose/webhook.pub`.
No tenant secret exists anywhere. The cost is that the edge must buffer
the body (up to 1 MiB, in memory) to hash it before it sends the
headers. Decision 7.

### 3.9 Limits and egress

| Limit | Value | Why |
|---|---|---|
| Request body | 1 MiB; 413 when `Content-Length` says more, before any wake; a chunked body past it is cut | GitHub allows 25 MB but typical events are kilobytes (*unverified* distribution). Decision 9 |
| Reply body | 64 KiB, listed types only | 3.4 |
| Rate per route | 10 a second, burst 50; 429 past it | Stripe sends bursts at month start (Stripe docs, "Handle events asynchronously"). 429 is a retryable failure everywhere |
| Rate per project | 30 a second; 8 requests at a time | One project cannot hold the edge's connections |
| Unknown tokens per source address | 20 a second, then drop | 404s are the scan case |
| New connections on :443 per source | 256 open, 100 a second | Stripe's 15 addresses carry every tenant's deliveries, so the cap must be far above :22's 64 and 20 a second |
| Routes per project | 20 | |

A per-source cap alone would be wrong here. Providers send from a few
shared addresses, so a cap per source would let one tenant's Stripe
burst throttle every other tenant's Stripe deliveries. Rates are
therefore per route and per project; the per-source limits apply only
to unknown tokens and to raw connection counts.

**Egress.** Request bytes reach the edge from the internet, which Azure
does not bill, then travel to the host over WireGuard. Reply bytes
leave the edge to the internet. I-1063's `guest_meter` cannot see them:
they leave the guest on port 22 to the edge, where they look like a
terminal's output. The edge counts reply bytes per project and reports
them with each delivery (3.10); the rollup adds them to the project's
egress beside `coalesce(net_egress, net_tx)`. This amends I-1063's
"Not done" note. At the caps, one project can send at most 30 x 64 KiB
a second, about 160 GB a day, so the count matters for abuse even
though real replies are a few hundred bytes. Decision 10.

### 3.10 What the user sees, and what is logged

Per route, the api keeps the last 20 deliveries:
`(at, status, outcome, duration_ms, bytes_in, bytes_out)`. `outcome` is
lower_snake: `delivered`, `woke`, `stopped`, `started`,
`start_refused`, `no_listener`, `timeout`, `too_large`,
`rate_limited`, `body_dropped`. The edge sends them in batches every
10 s to `POST /internal/webhook-deliveries`. `repose webhooks` shows the
newest; `--json` and the dashboard show all 20.

The edge logs one line per delivery with event `webhook_delivery`,
`project_id`, `route_id`, `status`, `outcome`, `ms`, `bytes_in`,
`bytes_out` and `source_prefix` (the /24, as the SSH gateway logs).
Never the path, which holds the token; never the query, a header
value or a body byte. The handler must not log `r.URL`, and neither may
any error path (a TLS error from Go's `http.Server` names the address
only). A test greps the logs for markers planted in each of those
(section 10).

Metrics: `repose_gateway_webhook_requests_total{outcome}`,
`repose_gateway_webhook_wake_seconds` and
`repose_gateway_webhook_inflight`.

## 4. End-to-end request path

1. Stripe POSTs to
   `https://hooks.repose.herakraft.co/<pid>/stripe/<token>`.
2. DNS gives the edge's public address. nftables accepts :443 under the
   per-source connection limits.
3. The gateway's :443 listener completes TLS. SNI
   `hooks.repose.herakraft.co` selects the `autocert` certificate; any
   other name falls through to the preview stub as today.
4. The webhook handler parses the path. A malformed path is 404.
5. It looks up `sha256(token)` in its route table, which it keeps in
   memory from `GET /internal/webhook-routes?since=<version>` every 5 s.
   The project id and route name must match the row. No row: 410 if
   the hash is a tombstone, else 404. Nothing has called the api or
   touched a host.
6. Route and project rate limits, then the in-flight count. A
   `Content-Length` over 1 MiB is 413.
7. Project state from the cached `/internal/route?project_id=`: the
   section 3.6 table. Frozen: `POST /internal/wake` with reason
   `webhook`, inside an 8 s budget.
8. SSH to `guest_ip:22` over `wg0`, with the 5-minute gateway
   certificate, reusing a connection the project's last delivery opened
   if it is less than 30 s idle. It opens `direct-tcpip` to
   `127.0.0.1:<port>`, or `::1` when the port listens only there. A
   refusal from sshd ("connect failed") is 502 with `repose: nothing is
   listening on port 3000`, outcome `no_listener`.
9. It writes the HTTP/1.1 request (section 3.4) and streams the body
   with a byte counter.
10. It reads the reply under the 30 s timeout, applies the reply rules,
    and streams the status, headers and allowed body back to Stripe.
11. It adds the delivery to the next batch for the api and logs the
    line in 3.10.

The app sees a request from `127.0.0.1` with Stripe's body and
`Stripe-Signature` intact, and `constructEvent` passes.

## 5. Failure modes

| Failure | Behaviour | What the user sees |
|---|---|---|
| Wrong or guessed token | 404 at step 5 | Nothing; it never reaches the machine |
| Route deleted, token rotated, project destroyed | 410 for 30 days | The delivery list on a live route; nothing on a deleted one |
| api down | Route table and state cache keep working for up to 1 h from the last sync, as the revocation cache does (06-gateway-edge.md §6). A wake or a start needs the api, so a frozen machine gets 503 `Retry-After: 30` | Deliveries resume when the api returns; batches the edge could not send are dropped after 10 minutes, and the counts are then missing |
| Edge down or redeployed | `gateway handover` passes the listener to the new process (`nix/edge/default.nix:388`). A real outage refuses connections | Providers retry; GitHub does not. One edge VM is one point of failure for SSH and webhooks alike |
| Wake fails | 503 `Retry-After: 30`, outcome `wake_failed`, the existing `guest_wake_fail` log | `repose webhooks` shows 503 |
| Nothing listening on the port | 502, outcome `no_listener` | The provider's dashboard shows the repose message; `repose webhooks` shows 502 |
| App slower than 30 s | 504, outcome `timeout` | Same |
| App answers 3xx | 502 | Same; the app's redirect is a bug for the provider too |
| App answers HTML | Status kept, body dropped | `Repose-Body-Dropped: type` on the reply |
| Host lost | 503 `Retry-After: 300` | Same as an SSH attach |
| Plan memory full when `--start` fires | 503, outcome `start_refused` | An event, as a refused `repose start` makes |
| Machine stopped, provider auto-disables (Slack, Shopify, Polar) | The provider stops sending | The webhooks docs page warns, and the delivery list shows a run of 503s |
| Token leaked | `rotate`, or add-then-remove for no gap | |
| Unused notice (I-262) | Deliveries do not count as use, so a machine that only receives webhooks is announced as unused, and `repose stop --unused` would stop it | The notice gains `got 41 webhook deliveries` for such a machine, so the user is not surprised |
| Body over 1 MiB | 413 before any wake | Provider dashboard |

## 6. Abuse: why this does not reopen the preview case

Public previews were designed with a `preview: public` switch and
called "a way to serve content from a guest to the internet"
(`docs/features/ports-and-previews.md:167-170`). The owner did not
approve them on 2026-09-25 (`docs/proposals/2026-09-24-backlog-triage.md:14`),
and all four council members kept the public half shut: "Public mode
turns repose into a host for abuse"; owner-only links "keep the abuse
vector that stopped I-6 shut". What made a public preview dangerous was
that it served pages: phishing kits, malware downloads and live
products, under repose's name, paid for in repose's egress.

A webhook route serves no page:

- **No HTML, no script, no redirect, no cookie.** 3.4 drops every body
  type a browser renders, adds `CSP: sandbox`, turns 3xx into 502 and
  strips `Set-Cookie`. A phishing page, a download and an open redirect
  each need one of those.
- **64 KiB of reply.** Media and files do not fit.
- **Unguessable URLs per route.** Nobody finds a route by browsing or
  scanning; 128-bit tokens and a per-source limit on 404s make a scan
  pointless.
- **Rates sized for events.** 10 a second per route serves Stripe's
  bursts and is too slow for a site with real traffic.
- **Counted egress** (3.9), against the plan's allowance and its 4x
  stop.
- **The edge stores nothing** (3.7), so a takedown has no content to
  remove; the operator removes the route.

What stays open is narrower than what repose already allows.
`cloudflared` is a menu entry (I-251) and gives any guest a full public
URL with HTML, files and no rate limit (`machine.md:172-175`). A
webhook route adds a smaller, safer door. The one use it makes easier
is a live service whose users are other people, such as a Telegram bot
with real users. I-257's terms line ("don't serve production traffic to
other people") already covers that, and the webhooks docs page repeats
it once. Decision 11 asks whether the terms need a webhook sentence.

Reputation: a tenant can still put a route URL in spam as a link. The
link shows a short JSON or text reply, or nothing. If a blocklist still
marks the name, a separate domain (decision 2) keeps the dashboard and
Logto off it.

## 11. Risks

- **GitHub loses deliveries** while a machine is stopped, with `--start`
  off or on. GitHub's redeliver button is the remedy; the docs say so.
- **Auto-disable** at Slack, Shopify and Polar after hours of 503s. A
  user who stops a machine overnight can come back to a disabled
  subscription.
- **One edge.** SSH and webhooks share one VM and one public address.
  An outage or a flood on :443 also slows logins. Azure's basic DDoS
  protection is all there is (SECURITY.md).
- **The hostname is forever.** If it ships under `repose.herakraft.co`
  and the product moves domains, the old name must keep answering.
- **SSH per delivery** adds a handshake (tens of milliseconds,
  *unverified* on the edge). The 30 s connection reuse covers bursts; a
  provider that sends one event an hour pays the handshake each time.
- **Wake inside 3 s** for Slack and Discord is predicted from I-818's
  9 to 10 ms resume and not measured through this path.
- **A `Host` rewrite** can surprise an app that builds absolute URLs
  from `Host`. `X-Forwarded-Host` carries the public name, and the docs
  say so.
- **Abuse by a production bot** with real users stays possible, as it
  is through `cloudflared` today.

   daemon, reverse forwards, owner-only links), or after the forward

5. **Where routes live.** In the api with the CLI and dashboard

6. **Stopped machines.** 503 by default with a per-route `--start`, off
   by default (recommended), or on by default?

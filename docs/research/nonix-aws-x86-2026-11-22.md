# The x86 installer on a rented Intel server, as a customer (No-Nix PR 12, 2026-11-22)

**Status: measured. Every number below was taken on a virtual Intel
host with nested virtualization, not bare metal** (AWS `m8i.2xlarge`
with `NestedVirtualization=enabled`). The bare-metal run the program
asked for did not happen: see §1 and §9. Board item ENG-170, role
`spark x86`; the conductor's decisions during the run are quoted where
they changed the method.

The code under test is `main` at `74850e02`: `ops/install-host-x86.sh`
(DECISIONS I-1498), `repose host add` on linux/amd64, hostd from
`cmd/hostd`, against production (api `api.repose.run`, guest base
`2026.11.22.8`). The owner's account was used, as decision D-22 allows,
with a session minted by `ops/dev/dashboard-session`.

`hostd-linux-amd64` sha256 `e13877345d75ea3df070ba40931d7759d31ae9795682d3b0fe492b9dbfbeff1f`.

the owner's release-tag step, I-1496), so the installer was given

line today, without that flag, would fail at the manifest fetch; that
path was not run.

## 4. Finding 1: the plain `repose run` could not create a machine

`repose run e2e-x86-u1 --temp 3h --size small -d` in a scratch
directory with no git: **exit 8 in 0.33 s**, `repose has no room for
this machine. A machine holds its memory while it runs, so stopping one
frees room for it.` The same with `--host e2e-x86` and with `--size
tiny`. The api's answer to the same `POST /v1/projects`
(`placement: own`, no `guest_runtime`):

```
HTTP 503 {"error":{"code":"capacity","message":"no host with capacity","detail":{"hosted_allowed":true,"reason":"no_runtime_host"}}}
```

Production's default guest runtime was `nix` (`store.DefaultGuestRuntime`),
the CLI sends no `guest_runtime`, and a host installed without Nix runs
no nix guests (hostd at start: `nix guests off`, `reason nix_mode_off`),
so `scheduler.runtimeSQL` refuses it (I-1464). Two defects: a customer
on the x86 installer (or the Mac appliance) could not create any
machine, and the CLI turns `no_runtime_host` into the "no room"
sentence, which names the wrong cause. The conductor recorded and
assigned both and flipped production's default runtime to `erofs`
during the run (§8 for the plain command afterwards).

To keep measuring, `e2e-x86-u1` and `e2e-x86-u2` were created with
`POST /v1/projects {"class":"small","expires_in_s":10800,"placement":"own","guest_runtime":"erofs"}`
as the owner (a billing-exempt account may choose the runtime,
`createRuntime`). Every later step used the CLI.

## 5. Finding 2: the Claude login share fails on Ubuntu 24.04

At every guest start hostd logs:

```
{"ts":"2026-11-22T14:10:33Z","level":"WARN","msg":"guest starts without the login share","component":"hostd","guest_id":"01a20396-86b1-7014-91d7-6e38f60ffbae","project_id":"01a20396-869d-7ce8-a123-18bae692e917","event":"auth_share","err":"virtiofsd exited before creating its socket; see journalctl -u virtiofsd-auth@01a20396-86b1-7014-91d7-6e38f60ffbae"}
```

and the unit:

```
virtiofsd[6821]: error: unexpected argument '--translate-uid' found
systemd[1]: virtiofsd-auth@01a20396-86b1-7014-91d7-6e38f60ffbae.service: Main process exited, code=exited, status=2/INVALIDARGUMENT
```

The installer takes virtiofsd from apt; noble's is `1.10.0-1ubuntu0.1`,
which has `--uid-map`/`--gid-map` and not `--translate-uid`. The guest
boots without the share, so Claude Code's login does not persist
across machines on this host. Seen at 14:10:33, 14:11:37, 14:11:57 and
14:12:11 (every start and create).

## 8. Removing the host, and adding it again

`repose rm --yes e2e-x86-u1 e2e-x86-u2`: 0.49 s, both `DestroyGuest`
`ok` at 14:13:24. `repose host rm --yes e2e-x86`: 0.32 s, exit 0, at
14:13:27; `repose host ls` then `You have no hardware of your own.`

Run on the box itself, `host rm` changes nothing on it: hostd keeps
running and retries against a host the api has retired:

```
{"ts":"2026-11-22T14:13:34Z","level":"WARN","msg":"stream disconnected","component":"hostd","event":"stream_disconnect","err":"rpc error: code = PermissionDenied desc = host is retired","retry_ms":1011}
{"ts":"2026-11-22T14:13:36Z","level":"WARN","msg":"stream disconnected","component":"hostd","event":"stream_disconnect","err":"EOF","retry_ms":2130}
```

`own-hardware.md` says what `host rm` does on a Mac; for an x86 box it
says nothing about the box, and nothing says how to uninstall or how to
add the same box again.

An add of the same box again, tried for 23 seconds while the
owner's one host slot was free (14:35:18 to 14:35:41):

- `repose host add e2e-x86` (the name of the retired host): exit 0,
  a fresh line (412 bytes of stdout), and `repose host ls --json` shows
  the **same host id** `01a20394-ac2f-780c-923e-195832d73152`, state
  `waiting`, `registered_at` null, `last_heartbeat_at` 14:13:34 (the
  table: `e2e-x86 waiting 31 GB 0 0 22m ago`).
- The installer with the new join: exit 0 in 0.92 s, and
  `registered already (/var/lib/repose/hostd/host.json); the join
  argument is not used again`. `/var/lib/repose/hostd/` still holds the
  retired host's `host.json`, `cert.pem` and `key.pem`, so hostd keeps
  dialling as the retired host and the new add stays `waiting`.

So a customer who removes an x86 host and adds the same box again is
stuck, and nothing in `own-hardware.md`, troubleshooting or the
installer's `--help` says what to clear. The host was removed again at
14:35:41 to give the slot back; clearing the files and re-running was
not tried.

**`e2e-x86-u3` was not created.** After the conductor flipped
production's default runtime to `erofs`, the plain `repose run
e2e-x86-u3 --temp 3h --size small -d` was to be run on this host, but
the owner's account allows one host of its own at a time and the Mac
spark kept that slot for the rest of the day. The plain customer path
under the new default is proven on the Mac instead (PR 11's report).

## 9. What could not run

- **Bare metal.** The vCPU quota (16) admits no `.metal`; the increase
  to 72 was still `CASE_OPENED` at teardown. Every number here is from a
  virtual Intel host with nested virtualization. The quota request is
  still open; whoever runs the bare-metal check next starts there. A
  cold create there
  includes one more layer of virtualization than on bare metal; the
  image fetch, which is 94 percent of the cold create, does not depend
  on it.
- **The signed hostd channel.** `hostd-stable` is unpublished; hostd
  came from `--hostd-binary`.
- **The plain `repose run` after the runtime flip, and a clean re-add**
  (§8): the slot belonged to the Mac.
- **The printed line verbatim.** The installer ran from the copied file
  with the printed arguments plus `--hostd-binary` and `--size 60`, not
  through `curl | sudo bash`, because of the channel; the served file
  is byte-identical to the one run.

## 11. Findings, in order of customer impact

1. A host installed without Nix could take no machine while
   production's default runtime was `nix`, and the CLI said "no room"
   (§4). The default is now `erofs`; the CLI's sentence for
   `no_runtime_host` is still wrong.
2. Removing an x86 host and adding the same box again does not work:
   the old registration on disk wins, and nothing says how to clear it
   (§8).
3. The Claude login share never mounts on Ubuntu 24.04, because apt's
   virtiofsd 1.10.0 rejects `--translate-uid` (§5).
4. `repose host rm` on the x86 box leaves hostd running and retrying
   against a retired host forever (§8).
5. Cold create is 113 s, almost all of it the 2.87 GB base image at
   about 27 MB/s; warm create is 6.3 s, start 6.8 s (§6).
6. The installer itself is fast and idempotent: 14.5 s, online 27 s
   after it started, a second run 0.7 s that rewrites nothing, and a
   reboot that brings the host and its running machines back in 22 s
   (§3, §7).

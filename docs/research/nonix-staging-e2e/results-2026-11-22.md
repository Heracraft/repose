## Isolation (ops/checks/isolation-host01.sh, staging copy in checks/)

- **Result:** 18 PASS, 1 SKIP (direct-to-guest, by design), 1 FAIL.
- **The FAIL:** TestGuestSeesOneDisk saw `[vda vdb]`.
- **Why it fails:** an erofs machine has two disks by design: the read-only image and the writable volume.
- **What makes it safe:**
  - Inside the guest, `lsblk` shows vda RO=1.
  - `dd of=/dev/vda` as root fails with "Operation not permitted".
  - The host attaches the image with `readonly=on`.
- **Follow-up:** the test is updated by the host daemon builder.

## Findings

- **(a) Image modes.** 2026.11.22.5 and .6 had /etc and /usr at 0775. sshd's StrictModes then ignored the principals file, so every login was refused. `dump.erofs` 1.9.4 masks its Access field to 0777, so special bits need the raw inode: [erofs-mode.py](erofs-mode.py). The real modes are /tmp 1777 and sudo 4755. Fixed in .8 (modes stripped in the checkout).
- **(b) Base bump timing.** A non-security erofs base is marked pending only at the 04:00 UTC sweep; a security release is marked within 10 minutes (internal/api/basebump). The rotation test therefore publishes the second base as a security release. Measured: pending was set 454 s after publish.
- **(d) Fork SSH, verified.** A fork that reuses a just-freed guest IP is unreachable for about 30 s or more. The host's neighbour entry keeps the destroyed guest's MAC (STALE, then FAILED), and the gateway's dial times out. One host-side ping resolves it. This is not erofs-specific. Candidate fixes: `ip neigh del` when hostd frees or assigns an IP, or a gratuitous ARP from the guest at boot.
- **(e) 10.5 s wake, verified.** The gateway caches routes for 5 s (RouteTTL) and dials with a 10 s timeout. An exec less than 5 s after a pause dials the frozen guest, times out, then looks up the route again and wakes it. Measured on the same host the same day: Nix 10.55 s and erofs 10.51 s within 2 s of a pause; erofs 0.44 s with an 8 s gap. This is the accepted path of DECISIONS I-822.
- **(f) Slow start/stop ops, unverified.** In cycles 2-4 the api took 2.7 s to receive hostd's result and then about 7.85 s before it set the state, with nothing logged in between. One repro attempt did not reproduce it.
- **Other:** a fork keeps the source's /etc/machine-id, because it is persisted on the volume.

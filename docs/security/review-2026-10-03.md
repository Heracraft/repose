# Security review, 2026-10-03 (whole repo and a live guest)

Reviewed: the tree at `main` `e69c1e5`, checked out in a fresh worktree,
plus the guest this review ran on (a repose guest on host-01). The
reviewer was `dev` with passwordless sudo, the position any tenant has.

Rules kept: nothing was sent to production beyond a few single TCP
connects and local reads on this guest. No auth attempts, floods, or
requests to the host caches, gateway or api. No secret value was printed
or copied; secrets are named by file or variable name only. Local
reproduction used throwaway Postgres and Nix builds inside this guest or
in the scratchpad, never against production.

## Scope and method

Areas hunted: the api PKI and `/internal` listener, host enrolment and
revocation, secret envelope and fork, the SSH gateway (auth, revocation,
session lifetime, connection limits, banners, previews), the shared Nix
store export, hostd's guest-event and metering ingest, the guest-to-host
notify and question paths, snapshot restore and abuse holds, the Nix
build path on the host, the CLI browser bridge and input proxy, the
Claude login share, the notification chain, thin-pool and conntrack and
disk-IO limits, and the CI/supply-chain workflows.

Each candidate was put through three adversarial lenses: a code-path
reading from source to sink, an exploitability argument against the
threat model, and a reproduction (a local test or a safe read on this
guest). A finding is counted confirmed when at least two lenses failed
to refute it. Where the lenses disagreed on severity, the code was read
again here and the severity set by that reading, not by vote count.

## S-1 (critical) Tenant config build on the host nix-daemon reaches IMDS and the storage managed identity

Attacker: (c) a malicious or compromised tenant guest. Any authenticated
tenant who can push a project config fragment. No special privilege.

Location: `internal/hostd/nixbuild/nixbuild.go` (build runs
`nix build --option sandbox true` via `NIX_REMOTE=daemon` as the
`nixbuild` user, so builders are spawned by the host nix-daemon; on
failure the `nix log` tail is returned to the tenant),
`nix/hosts/nftables.nix:214-232` (IMDS/wire-server/mesh/private-range
drops are scoped to `iifname "br-guests"`; the `output` chain is
`policy accept` with no rules), `nix/guest/contract.nix` (the fragment is
a full home-manager module; `home.packages` is unrestricted),
`nix/hosts/host-01.nix:43-50` (`id-repose-host`, Storage Blob Data
Contributor on the shared snapshot container).

Attack path: a fragment is evaluated and built by the host's nix-daemon.
The eval guards (`restrict-eval`, `pure-eval`, no IFD, `allowed-uris`)
bound evaluation only. A fragment can embed a fixed-output derivation
(FOD) in the system closure. In CppNix a FOD is the one build type given
network access: its builder does not get a private network namespace and
runs in the host's netns. The host nftables drops IMDS, the wire server,
the mesh and private ranges only for forwarded guest traffic; the
`output` chain for host-originated traffic is empty with `policy accept`.
So the FOD builder, on the host in the host netns, can reach
169.254.169.254 (IMDS) and fetch the host's managed-identity token for
the shared snapshot container, then exfiltrate it (outbound from the
host, or through the `nix log` tail returned on a forced hash mismatch).
With Storage Blob Data Contributor the attacker reads and overwrites
every tenant's snapshot blobs. Combined with S-26 (no restore checksum),
overwriting a victim's blob gives cross-tenant code execution on their
next restore.

Evidence: reproduced on this guest (Nix 2.34.8, daemon `sandbox=true`). A
bare FOD builder that ran `ip -o addr show` saw the host's real
interfaces (`eth0 10.64.0.8/22`, `wg-repose 10.255.254.1/32`, `docker0`,
a veth), proving FOD builders execute in the host network namespace,
while a non-FOD builder under the same sandbox saw only `lo`. The build
then failed with `hash mismatch`, confirming the builder command runs
before the hash check. No token was fetched: from this guest the guest
NIC path to IMDS is blocked, which is why this finding is the host-daemon
path, not the guest NIC. SECURITY.md boundary "IMDS is blocked from
guests" considered only the guest NIC path.

Fix: deny the FOD build path the host's privileged network. Preferred:
run tenant builds in a dedicated build netns (or a throwaway build
microVM) with only plain internet egress, no route to IMDS, the wire
server, the mesh, the caches or Postgres, and no managed identity.
Minimal: in the `output` chain, drop traffic to 169.254.169.254,
168.63.129.16, 10.64.0.0/12 and the private/mesh ranges when it comes
from the build users (match the nixbld uid range or the nix-daemon build
cgroup) so hostd and operator traffic are unaffected. Also scope the
snapshot identity to per-tenant least privilege rather than a
container-wide Data Contributor reachable from builds, and enforce the
documented restore checksum (S-26). Update the SECURITY.md boundary: the
IMDS block must cover host-originated build traffic, not only
`br-guests`.

## S-2 (high) `/internal` on 8444 trusts any host-CA client cert as the gateway

Attacker: (c) a malicious guest that has escaped to its host, or anyone
holding one host's `/var/lib/repose/hostd/{cert,key}.pem` (root on one
host), with network reach to the control VM's 8444.

Location: `internal/api/app/app.go:336-339` (the `/internal` listener
clones the hostMgr TLS config and sets only
`ClientAuth = RequireAndVerifyClientCert`),
`internal/api/hostmgr/hostmgr.go:126` (`ClientCAs: s.ca.Pool()`),
`internal/api/hostmgr/hostmgr.go:280,338` and
`internal/admin/cmds.go:1422` (host certs and the gateway cert both come
from `IssueClient` on the same X.509 CA),
`internal/api/http/routes.go:78-87` (internal routes registered with no
per-route identity check), `internal/api/http/internal.go:111-140`
(`internalGatewayCerts`), `internal/api/ca/ca.go:235-266`
(`IssueGatewayCert` signs a User-CA cert with principal = project id for
any project), `internal/gateway/server.go:403-441` (authenticate checks
the User CA, validity, revocation and the project-id principal; never
inspects `key_id`).

Attack path: one X.509 CA signs both host client certs (CN = host id) and
the gateway's client cert. The `/internal` listener's `ClientCAs` is that
CA's pool and nothing checks the peer CN in TLS or in any handler. So a
host cert passes as the gateway on every `/internal` route. The worst
route, `POST /v1/internal/gateway-certs`, returns a 5-minute User-CA cert
with principal = any project id, with no tie between the project and the
caller. The public gateway accepts that cert as a user login, giving a
shell as `dev` in any tenant's guest on any host. `/internal/route` also
maps any `<slug>.<handle>` to its project id. This breaks SECURITY.md
boundary 4 ("per-host mTLS stops a compromised host acting on another
host's guests").

Evidence: reproduced with the real `internal/api/http` package against a
throwaway Postgres: a test served `InternalHandler` with the TLS config
built as in `app.go` and authenticated with a host-style client cert,
then requested a gateway cert for another project; status 200 and a
User-CA-signed cert with principal = the victim project id came back.
Reachability of 8444 from VNet members is recorded in review-2026-09-21
M5-4.

Fix: authenticate the gateway explicitly. Either issue the gateway cert
from a separate CA (or a dedicated EKU/OU) and set the `/internal`
listener's `ClientCAs` to that CA only, or wrap `InternalHandler` in
middleware that requires
`r.TLS.VerifiedChains[0][0].Subject.CommonName == "<gateway>"` and
rejects any CN that parses as a UUID. Defence in depth: have the gateway
reject user certs whose `key_id` ends in `:via-gateway`. Add a test that
a host cert gets 403 on every `/internal` route.

## S-3 (high) `bump-agents` runs downloaded binaries with a write token on an unprotected `main`

Attacker: (e) a compromised upstream release channel or maintainer
account for any of the six bundled agents, or a hijacked
`cachix/install-nix-action@v31` tag.

Location: `.github/workflows/bump-agents.yml:12-14` (`contents: write`,
`pull-requests: write`), `:20` (`actions/checkout@v4`, default
`persist-credentials`), `:26` (`cachix/install-nix-action@v31`, mutable
tag), `:35-37` (`GITHUB_TOKEN`/`GH_TOKEN` in the step env),
`scripts/bump-agents.sh` (version/URL from upstream `latest`; hash taken
from whatever downloaded; `nix build` then
`HOME=$(mktemp -d) "$out/bin/$b" --version`, unsandboxed, inheriting the
token env).

Attack path: every day the job resolves each agent's latest upstream
version, downloads it, records the hash (trust on first use, no signature
check), builds it, and runs the binary with `--version`. That process
inherits `GITHUB_TOKEN`/`GH_TOKEN` with `contents:write`, and checkout
leaves the token in `.git/config`. A trojaned upstream release can read
the token and push a commit straight to `main`; `gh api` confirms the
repo is public, `branches/main/protection` returns 404, and there are no
rulesets. Coolify redeploys api, api-grpc and the dashboard on every push
to `main` (I-112), so the payload reaches production. The same token can
create a release with a backdoored CLI, which `install.sh` trusts (S-27).

Evidence: read-only `gh api` calls confirmed the public repo, no branch
protection, no rulesets, and default read workflow permissions overridden
to write by this workflow. A local demo of the exact
`HOME=$(mktemp -d) "$out/bin/$b" --version` invocation with dummy token
values showed the child process reading both token variables. Nothing was
run against GitHub or production beyond read-only GETs.

Fix: split the job. A first job with `permissions: contents: read`, no
token, and `env -i` around the `--version` call resolves/prefetches/
builds and passes `versions.json` as an artifact. A second job with the
write permissions only commits and opens the PR and executes nothing it
downloaded. Set `persist-credentials: false` on checkout. Pin every
third-party action by commit SHA and turn on `sha_pinning_required`.
Protect `main` with a ruleset (require a reviewed PR, block force-push,
keep `github-actions[bot]` off the bypass list). Deploy Coolify from a
protected branch or tag, not every push. Verify upstream provenance
(npm provenance, GitHub attestations) before recording a hash.

## S-4 (medium) Retired or lost hosts keep a valid mTLS identity

Attacker: a holder of one host's client cert, after the operator has
marked the host `lost` or `retired`.

Location: `internal/api/hostmgr/hostmgr.go:328-345` (`Rotate` checks only
that the row exists, then issues a fresh 30-day cert), `:362-370`
(`Session` same existence-only check), `internal/admin/cmds.go:200-235`
(`hosts retire` / `hosts mark-lost` only `UPDATE hosts SET state=...,
draining=true`). `cert_serial` is written on Register and Rotate and
never compared; the X.509 CA has no CRL.

Attack path: `retire`/`mark-lost` keep the row, so `Rotate` and `Session`
still succeed for a compromised host's identity. The attacker rotates
every 25 days and keeps a valid cert forever. Chained with S-2, this is
permanent ability to mint User-CA certs for every project. The only cure
today is a full `ca rotate --host`.

Evidence: reproduced against a throwaway Postgres. A host row set to
`state='lost', draining=true`, then a real `HostService.Rotate` over
mTLS with a client cert whose CN is the host id, returned a fresh cert
and key. The admin subcommand is `hosts mark-lost` (the original finding
wrote `hosts lost`).

Fix: in a shared check used by `Rotate`, `Session` and the `/internal`
identity check (S-2), refuse hosts in state `retired` or `lost`. Compare
the presented leaf serial with `hosts.cert_serial` (allow the previous
serial during a short rotation window) and have `mark-lost`/`retire`
clear `cert_serial`. Add a test that a lost host's `Rotate` and `Session`
return `PermissionDenied`.

## S-5 (medium) Gateway forgets revocations after 13h while user certs last 24h

Attacker: a holder of a stolen laptop's cert and key, or any cert the
owner revoked with `repose logout` from another device.

Location: `internal/gateway/cache.go:25-28` (`revocationKeep = 13h`;
comment still says certs live 12h), `:57-79` (`Refresh` drops serials
older than `revocationKeep`, then fetches incrementally),
`internal/ca/sshca/sshca.go:19` (`UserCertTTL = 24h`, I-267),
`internal/api/ca/ca.go:355-356` (`RevokedSince` returns only
`revoked_at > since`).

Attack path: I-267 raised the user cert lifetime to 24h, but the
gateway's in-memory revocation set forgets each serial 13h after it first
sees it. Refreshes are incremental, so an evicted serial never returns
unless the process restarts. A cert revoked in roughly its first 11 hours
becomes usable again for the rest of its 24h validity. I-267 claims
`repose logout` revokes a lost laptop's certs at once; on a long-running
gateway that holds for 13h only.

Evidence: reproduced with the real `internal/gateway` package and the
in-repo fake api. Right after revoke the cert was refused; 13h05m later
the same (still-valid-24h) cert authenticated. A gateway restart
re-primes the cache with a full fetch and closes the window, so
exploitability depends on gateway uptime.

Fix: carry `expires_at` in `/internal/revoked` and evict each serial only
after its cert expiry plus clock skew. Minimal:
`revocationKeep = sshca.UserCertTTL + 1h`, derived from that constant,
with a test that ties the two together.

## S-6 (medium) One source address can fill all 200 gateway slots pre-auth

Attacker: an unauthenticated internet client with one IP.

Location: `internal/gateway/server.go` `HandleConn` (acquires the global
slot before the per-source limiter; `AuthTimeout` is the only bound on an
idle pre-auth connection), `internal/gateway/limits.go:16-18`
(`DefaultMaxConns = 200`, `DefaultAuthTimeout = 30s`),
`cmd/gateway/serve.go:38-46` (production passes neither, so defaults
apply), `nix/edge/default.nix:217` (`tcp dport 22 accept`, no rate or
count limit).

Attack path: the global connection counter is taken before the per-source
limiter. A connection marked busy or over-limit still holds its slot
through the handshake up to the 30s `AuthTimeout`; only connections that
reach the public-key callback are refused, and a client that sends
nothing never gets there. One address opening 200 idle connections, each
reopened as it times out (about 7/s), holds every slot. Authenticated
relays share the same 200-slot pool with no per-user cap.

Evidence: reproduced with the real Gateway at production defaults. 200
idle TCP connections from one source filled the pool; a legitimate dial
with a valid cert got `gateway busy`.

Fix: check the per-source limit and ban before acquiring a global slot,
and close banned/over-limit connections immediately without a handshake.
Give the pre-auth phase its own short deadline and its own budget
separate from established relays, and add a per-user relay cap. Add
nftables `ct count over N` per source and a new-connection rate limit on
tcp/22 at the edge.

## S-7 (medium) Shared `/nix/store` export exposes other projects' fragments and the host system closure

Attacker: (b)/(c) any tenant with a shell in their guest.

Location: `internal/hostd/nixbuild/nixbuild.go` (each build copies the
project's fragment dir into the host store as `<hash>-source`),
`nix/hosts/virt.nix` (the whole `/nix/store` is shared read-only to every
guest), `docs/SECURITY.md` (claims the export stops "enumerating other
tenants' closures").

Attack path: the `.links` farm is masked by a tmpfs, but the store
directory itself is listable. Any guest can list and read other
projects' `fragment.nix` (user-authored Nix) and every guest and host
system closure, including the host closure's `hostd.service` flags (api
address, Blob account/container, managed-identity id) and the nftables
and sshd configuration. The `.links` mask was the only enumeration
control, and it does not cover a `readdir` of the store root.

Evidence: on this guest, `/nix/.ro-store` is a listable directory with
~10,313 entries; 10 `*-source` dirs hold a readable `fragment.nix`, and
~31 `nixos-system-host-01-*` closures are present. `.links` is empty
(masked). No secret value was read; a grep for private-key markers in the
host closure's `etc` found none.

Fix: give each guest a per-guest export containing only the paths in its
own closure (bind-mounts of those store paths, or a per-revision store
image), or build in a separate store that is not exported. Present the
export root as search-only so lookup-by-hash works but `readdir` fails,
after checking the guest nix-daemon tolerates `EACCES` on the lower
layer. Keep host system closures out of the exported store. Correct
SECURITY.md and `01-host-nixos.md` §5 until the fix lands.

## S-8 (medium) Guest-controlled `Warning.kind` becomes an unbounded Prometheus label

Attacker: (c) root inside a guest, replacing or impersonating guestd on
vsock.

Location: `internal/hostd/guest/create.go:740-742` (the `Notify_Warning`
case forwards `Kind` and `Detail` with no cap, unlike the adjacent
AgentEvent/Question cases which truncate to 1024),
`internal/api/events/events.go:310-312`
(`HostWarningsTotal.WithLabelValues(kind)` plus a log of kind and
detail), `internal/api/metrics/metrics.go:120` (the CounterVec is never
reset), `internal/hostd/vsockrpc/vsockrpc.go:25` (`MaxFrame = 4 MiB`).

Attack path: hostd forwards guest Warning kinds with no length cap,
allowlist or rate limit. The api uses `Kind` directly as a Prometheus
label value, so each distinct kind (up to ~4 MiB per frame) creates a
permanent time series. One guest can grow api memory and the `/metrics`
payload without bound, affecting every tenant on that api. The same path
writes guest-chosen `Detail` and `Kind` verbatim to the api log, against
the never-log rule.

Evidence: reproduced by sending 2000 `HostWarning` events through the
real `events.Ingest.OnEvent` against a throwaway Postgres: 2000 distinct
series in `repose_api_host_warnings_total` and the guest-chosen detail
string written verbatim to the log. hostd also holds up to 10,000 unacked
events (up to ~4 MiB each) in `stream`, a second memory pressure point.

Fix: in hostd, map warning kinds to a fixed allowlist (else `guest_other`),
cap `Detail`, and rate-limit notifies per guest. In the api, allowlist
the kind before `WithLabelValues` and drop or redact detail from logs.

## S-9 (medium) Unrate-limited, uncapped guest Notify messages

Attacker: (c) root inside a guest.

Location: `internal/hostd/guest/create.go:710-742` (`handleNotify`
forwards Agent, Kind, TmuxWindow, Options with no cap; only Summary/Text
cut to 1024), `internal/hostd/stream/stream.go:143-157` (pending map
capped at 10,000, oldest evicted; blocking send on a shared channel),
`internal/api/hostmgr/hostmgr.go:392-425` (one serial receive loop per
host), `internal/api/events/events.go` (AgentEvent insert; `agent_message`
skips dedupe; agent/tmux_window stored uncleaned), `0001_init.up.sql:229`
(agent/tmux_window are unbounded text; no retention job deletes events).

Attack path: root in a guest can send Notify frames as fast as it likes,
with large, varying `agent` strings. Kind `agent_message` skips dedupe,
so each becomes its own `events` row with unbounded agent/tmux_window;
nothing deletes these rows. Because the api handles each host's stream
serially, the flood also queues ahead of other tenants' command results
and heartbeats on that host, and past 10,000 pending events hostd evicts
other guests' state-change and snapshot events. Each AgentEvent also
writes a host journal line with tenant-controlled fields.

Evidence: reproduced against the real `internal/api/events` package and a
throwaway Postgres. 200 `agent_message` events with 400 KiB agent and
400 KiB tmux_window each grew the events table by ~170 MB in ~11s through
one ingest path, all acked and stored, with tenant text written to the
log. Verified severity medium (attributable, recoverable, no data
exposure); the original "high" is revised down.

Fix: in `handleNotify`, add a per-guest token bucket and cap/validate
Agent, Kind, TmuxWindow, Options and Warning.Detail. In the api,
allowlist `agent`, cap `tmux_window`, add a per-project hourly cap on
stored rows and a retention job. Keep host-originated events separate
from guest-originated ones in `stream` so a flood cannot evict them.

## S-10 (medium) One guest's bad `Sample` reply drops the whole host's metering batch

Attacker: (c) a malicious guest answering hostd's Sample request.

Location: `internal/hostd/guest/samples.go:83-95` (copies the guest's
`Signals.Agents` and `Procs` into the host-wide Samples unchanged),
`internal/api/meter/ingest.go:96-133` (queues every guest's rows into one
`pgx.Batch`, which runs as one implicit transaction; on error only
logs `samples_fail`), `internal/billing/rollup.go` (no samples -> a gap
row with zero running seconds and zero egress),
`internal/billing/gate.go:127-135` (the 4x egress hard stop reads that
egress).

Attack path: hostd copies the guest's `SampleResult` unvalidated. A value
Postgres refuses (a NUL byte in `ProcSample.comm`, or in an agent name
that lands in the `agents` jsonb) fails the whole batch, losing the rows
for every guest on the host. The rollup then records a billing gap with
zero egress, so the egress overage and the 4x hard stop read zero for
every co-hosted tenant. Host-measured tap counters are meant to be
guest-proof; this lets a guest zero them for itself and its neighbours.

Evidence: reproduced with `pgx` v5.7.6 (the repo version) against a
throwaway Postgres. A clean "victim" row and an attacker row with a NUL
`comm` queued in one batch both failed (`rows=0`): SQLSTATE 22021 for the
text column, 22P05 for the jsonb path. Verified severity medium
(metering/billing loss, operator-visible via `samples_fail`, no tenant
data exposed); the original "high" is revised down.

Fix: validate and clean guest-supplied sample fields in hostd (comm <=16
bytes printable no NUL; a cap on proc count; agent/window/state from
fixed sets or short printable strings). In the api, sanitize the same way
and insert each guest's rows in its own savepoint or batch. Write
host-measured fields in a statement that contains no guest-controlled
values. Alert on `samples_fail` per host.

## S-11 (medium) Edge hook ingest accepts platform-only notification kinds from guests

guest's owner.

Location: `internal/gateway/hookingest.go:73-110` (`POST /hooks` checks
only `kind != ""`, forwards agent/kind/summary verbatim; 10 req/s per
source IP), `internal/api/events/events.go:363-375` (`FromEdge` accepts

`billing_stopped`, `abuse_stopped`, `destroy_failed`, `temp_destroyed`,

## S-12 (medium) Overcommitted thin pool with no per-tenant bound

Attacker: (b)/(c) an authenticated tenant writing to their own volumes.

Location: `internal/api/scheduler/scheduler.go:86-110` (placement admits
a volume when the pool's physical free space is at least the volume's
virtual size; the sum of virtual sizes on a host is never bounded),
`internal/api/http/projects.go:669-697` and
`internal/hostd/guest/stop.go:187-200` (resize checks only the plan limit
and a 2 TiB cap, never the host pool), `internal/billing/plans.go:32-34`
(Pro 500 GB), `infra/azure/prod/prod.tfvars:16` (512 GB data disk per
host, one host).

Attack path: placement compares each volume's virtual size against
physical free space and never sums existing virtual sizes, and resize
never checks the pool at all. On prod the pool is ~486 GB on a 512 GB
disk, so one Pro project can be grown to 500 GB with a single resize
call, more than the whole pool. Writing real data past the ~5% autoextend
headroom exhausts the pool; dm-thin then queues writes for
`no_space_timeout` and fails them with EIO for every guest volume on the
host, plus the cache and snapshot volumes.

Evidence: dm-thin behaviour reproduced locally with loop devices (two
100 MB thin volumes on a 64 MB pool, `no_space_timeout` shortened for the
test): writes to both the attacker and the victim volume failed with "No
space left on device" and the pool switched to out-of-data-space mode.
The resize path (`projects.go` -> `stop.go` `lvextend`) with no pool
check is the strongest route. Verified severity medium (availability/
integrity, needs paid disk, attributable).

Fix: track the sum of `volume_bytes` per host (plus the cache volume) and
admit a placement or resize only when that sum stays within an explicit
overcommit ratio of pool capacity. Have hostd refuse a resize that would
exceed the pool budget. Set the pool to `error_if_no_space=1` so a full
pool fails fast. At ~90% usage, snapshot or freeze the largest writer and
page an operator rather than only warning.

## S-13 (medium) No per-guest conntrack cap

Attacker: (c) root in a guest.

Location: `nix/hosts/nftables.nix:182-189` (guest_in accepts the cache
ports with no limit), `:209` (per-guest new-flow rate of 200/s, but no
`ct count`), `nix/hosts/kernel.nix:27-40` (`nf_conntrack_max` and
timeouts left at kernel defaults).

Attack path: every connection a guest opens through the host takes a slot
in the host's single conntrack table. I-240 rate-limits new flows but
nothing caps how many tracked flows a guest holds; established TCP
entries last 5 days by default, and cache-port flows are not rate-limited
at all. At 200/s a guest reaches the default table size (~262k) in ~22
min; once full, the kernel drops every new flow host-wide, including
other guests' egress, the gateway's SSH over wg0, and the caches.

Evidence: confirmed by reading the ruleset and kernel config; this guest
shows `nf_conntrack_max = 262144` and the 5-day established timeout at
defaults. A namespace reproduction was not run (halted by a local safety
classifier, and a full exhaustion test would attack neighbours).

Fix: add a per-guest `ct count over N` drop (e.g. 20,000, keyed on
`ip saddr`) in guest_fwd and in the guest_in cache-port accepts.
Rate-limit new cache-port flows per guest. Set `nf_conntrack_max`
explicitly and shorten the established TCP timeout for forwarded flows.
Alert on `nf_conntrack_count / nf_conntrack_max`.

## S-14 (medium) Egress metering loses traffic on every start and stop

Attacker: (b)/(e) a tenant evading billing and the egress abuse ceiling.

Location: `internal/hostd/guest/samples.go:67-75` (delta counted only
when `cur.seen && tx >= cur.tx`), `internal/hostd/guest/create.go:363-374`
(teardown deletes the tap with no final `TapStats` read),
`internal/hostd/guest/stop.go:139-151` (only destroy takes a final
reading, from the nft counter), `internal/hostd/app/app.go:299-310`
(60s sample interval).

Attack path: the per-guest cursor (`m.last`) survives stop and start, but
a recreated tap's counter restarts at 0. The first sample after a start

Evidence: reproduced with the real `internal/hostd/guest` harness. Across

entirely between ticks metered 0 of 20 GB. running-seconds is

## S-16 (medium) Claude login share gives guests unbounded writes to the host root filesystem

Attacker: (b)/(c) any authenticated tenant, root or `dev` inside their
guest. No escape needed; the share is mounted rw for uid 1000 by design.

Location: `internal/hostd/guest/claudeauth.go:59-82` (the share is
created `0700 repose-auth` with no size, quota or content limit),
`internal/hostd/virtiofs/virtiofs.go:83-96` (read-write virtiofsd,

## S-17 (medium) Browser bridge forwards Authorization headers and response bodies

Attacker: a compromised or prompt-injected agent on the guest while the
user runs `repose browser bridge` into their laptop Chrome.

Location: `internal/cli/bridgecdp.go:731-793` (`scrubCookies`/
`scrubHeaderText` remove only `Cookie`/`Set-Cookie` and the cookie
lists), `:553-568` (filtered events do not include body readers),
`:594-636` (results whose id is not in `pendingIDs` pass through),
`:344-361` (`alwaysRefused` does not list `Network.getResponseBody`,
`getRequestPostData`, `Fetch.getResponseBody`).

Attack path: the bridge's stated boundary is that credentials cannot be
copied out of Chrome, and cookies are stripped. But `scrubCookies`
touches only cookie keys, so `Authorization` and other credential headers
in the already-forwarded network/fetch events go through verbatim, and
the response/request body readers are neither refused nor filtered, so
their results pass through raw. The incremental exposure over the
documented accepted gaps (page JS can read local storage) is credentials
the page's JS cannot read: HTTP Basic/Negotiate `Authorization` headers
the browser adds, tokens in bodies of HttpOnly-cookie-authenticated
endpoints, and, with `--allow`, cross-origin subresource bodies hidden by
CORS. These are session-equivalent and replayable after the bridge
closes, and no navigation-log entry records the traffic.

Evidence: reproduced with the real `internal/cli` bridge policy and the
package's fake-CDP harness. The cookie was stripped while `Bearer`,
`Basic` and `X-Api-Key` header values and a `getResponseBody`
`refresh_token` all reached the tool. Verified severity low-to-medium;
set to medium here because the broken guarantee is exactly the one cookie
scrubbing exists to provide, and the feature is advertised for
token-authenticated SSO/admin sites.

Fix: in `scrubCookies`/`scrubHeaderText`, strip `authorization` and
`proxy-authorization` (and a denylist of token headers) in the header
maps and header text; Chrome still gets the unredacted message because
the client-bound copy is scrubbed separately. Decide the body readers
explicitly: refuse `Network.getResponseBody`, `getRequestPostData`,
`getResponseBodyForInterception`, `Fetch.getResponseBody`, `IO.read` and
`Network.loadNetworkResource`, or restrict them to same-origin
allowlisted hosts. Strip `postData` from request events. Correct the
`your-chrome.md` "can't copy them somewhere" guarantee and the I-311 gap
list.

anyone who can forge a release can usually also rewrite `install.sh`
(served from the same repo); the exploitable root is the S-3 token chain.

Fix: sign releases (cosign keyless on a tag workflow, or
`actions/attest-build-provenance` with `id-token: write`) and have
`install.sh` verify against the expected workflow identity before
trusting `checksums.txt`. Protect `v*` tags with a ruleset and keep
`contents:write` away from workflows that run untrusted code (S-3).

## S-28 (low) `Audits` domain unfiltered; `issueAdded.rawCookieLine` can leak a rejected Set-Cookie value

Attacker: a malicious/prompt-injected guest with a bridge open.

Location: `internal/cli/bridgecdp.go:553-568` (filtered events include no
`Audits.*`), `:603-605` (an unlisted event passes through unmodified),
`:344-361` (`alwaysRefused` does not list `Audits.enable`).

Attack path: `Audits.enable` is forwarded and no `Audits.*` event is
filtered, so `Audits.issueAdded` passes through verbatim. Chrome fills
`CookieIssueDetails.rawCookieLine` with the full raw Set-Cookie header for
lines it cannot categorize, so a tool that calls `Audits.enable` can
recover a Set-Cookie value the scrubber is meant to hide. Narrower than
S-17: rawCookieLine is set only for cookies Chrome rejected, so the leaked
value belongs to a cookie the browser never stored.

Evidence: reproduced with real Chromium 153 on this guest. A Set-Cookie
with a non-ASCII `Domain` attribute (`WarnDomainNonASCII`) put the full
raw line, HttpOnly value included, into `issueAdded`; well-formed excluded
cookies showed only `{name,path,domain}`. The real bridge policy
forwarded `Audits.enable` and the event unchanged.

Fix: refuse `Audits.enable`, or add `Audits.issueAdded` to the filtered
events and strip `rawCookieLine` and any cookie-value fields before
forwarding.

## S-29 (low) Drop guard is name-based; non-hidden secret paths and symlinks to hidden targets upload

Attacker: (c)/(d) a guest-side agent that persuades the user to paste an
absolute path, or benign pre-existing laptop state.

Location: `internal/cli/inputproxy.go:309-342` (the systemDirs + `/.`
guard in `dropPath`), `:482-517` (`files` -> upload), `:520-527` (upload
via `os.Open`, which follows symlinks).

Attack path: the anti-exfiltration guard rejects only system dirs and any
path containing `/.`. It does not cover non-hidden secrets
(`~/Downloads/key.pem`), which upload cleanly if the user pastes the path,
and it checks the pasted string not the resolved target, so a non-hidden
symlink whose target is a hidden/secret file is read and uploaded. No
silent auto-exfiltration: the direct path needs the user to paste a
specific path, the symlink variant needs a pre-existing laptop symlink the
guest cannot create.

Evidence: reproduced with the real `localRegularFile` against a temp dir.
A `.ssh/id_ed25519` path was rejected; a non-hidden symlink to it, and a
non-hidden `.pem`, were accepted (quoting/escaping variants too).

Fix: resolve the path with `EvalSymlinks` and re-apply the hidden/system
checks to the resolved target. For a single file outside the synced
checkout that the user typed, surface a visible confirmation naming the
file. Optionally deny well-known secret patterns.

## S-30 (low) Unknown JWT `kid` forces a JWKS refetch on every request

Attacker: an unauthenticated internet client.

Location: `internal/api/auth/jwks.go` `key()` (calls `refresh()` whenever
the kid is not cached, with no negative cache, singleflight or minimum
interval; the keyfunc runs before signature verification), and the
`authed` middleware calls `Verify` before the per-user rate limiter.

Attack path: a token needs only a parseable header with an allowed alg and
a fresh `kid` (no valid signature), and every such request makes the api
fetch Logto's JWKS. 1:1 amplification through the api's IP, with the
per-user limiter running only after verification. Impact on legitimate
users is limited because a failed refresh keeps cached keys for up to 24h.

Evidence: reproduced against an httptest JWKS server: 100 forged tokens
with random kids produced 100 fetches; 100 with a known kid produced 0.

Fix: coalesce refreshes with singleflight and allow at most one refresh
per N seconds after the last attempt (recording the attempt time even on
failure); otherwise return "unknown key id" without fetching. Optionally
a per-IP pre-auth limiter in `authed`.

## S-31 (info) Preview hostname parser is ambiguous when a handle contains a dash

Latent; previews are not built (DECISIONS I-6).

Location: `internal/gateway/preview/preview.go:33` (greedy slug regexp),
`:35-39` (a comment that wrongly claims the split is unambiguous).

`<port>-<slug>-<handle>` cannot be split uniquely when handles may contain
`-` (they can: `DeriveHandle` keeps GitHub-login dashes). A dashed handle
cannot be routed at all under this scheme, and once proxying ships a user
could take over another user's preview origin. Reproduced: the real
regexp maps `3000-todo-app-hera-craft` to slug `todo-app-hera`, handle
`craft`. Fix before previews ship: a separator slugs and handles cannot
contain, or an opaque per-project preview id; correct the comment.

## S-32 (info) Unsubscribe tokens never expire and a GET changes state

Location: `internal/api/notify/unsubscribe.go` (`Sign`/`Verify` use
HMAC(user_id) with no expiry or nonce), `internal/api/http/notify.go`
(GET sets `notify_email=false` and deletes queued email outbox rows).

A link from any old email works forever, and a link scanner fetching it
with GET turns off the user's email notifications; the error text says
"or has expired" though tokens never expire. The non-expiry is a
documented choice (I-49); impact is limited to the user's own agent
notification emails, reversible from the dashboard. Fix: show a confirm
page on GET and act on POST (RFC 8058 List-Unsubscribe-Post), and drop
the misleading "or has expired".

## S-33 (info) Build log redaction misses multi-line and sub-4-byte secret values

Location: `internal/api/buildlog/buildlog.go` (`SetRedactions` drops
values under 4 bytes; `Append` is a per-line substring replace),
`internal/api/ops/phases.go:443-451` (the fragment-rejection check uses
the same whole-value match).

A multi-line secret (a PEM key) never matches a single log line, so its
lines store in `build_logs` in plaintext; short and encoded forms also
pass. No cross-tenant attacker: builds on the host have no secret env or
files, so the only way a secret reaches a build input is the owner
putting it in their own fragment, and only the owner reads their logs.
Fix: also redact each non-trivial line (and the base64 form) of a
multi-line value, and apply the same per-line check in the
fragment-rejection loop; or reword the doc.

## S-34 (info) Unpinned third-party actions and `@latest` tools in CI

Location: `.github/workflows/ci.yml`, `release.yml:22-25`,
`infra.yml:30,73`, and `bump-agents.yml:26` (all third-party actions by
mutable major tag; `go install golangci-lint@latest`;
`goreleaser-action@v6` with a floating GoReleaser v2 under
`contents: write`; `sha_pinning_required` is false).

A hijacked tag or compromised GoReleaser release runs with a write token
on a `v*` tag push and can alter release assets, which compounds S-27.
Fix: pin every action by commit SHA (Dependabot to bump), set
`sha_pinning_required`, pin GoReleaser and golangci-lint to exact
versions, and move `id-token: write` in `infra.yml` to the job that needs
it.

## S-35 (low) Host-to-guest traffic is unshaped

Location: `internal/hostd/net/net.go:248-300` (only an ingress policer on
the tap; the host-to-guest direction is unlimited).

A guest can pull data at the host NIC's full receive bandwidth,
contending with other guests' downloads and with the WireGuard tunnel to
the edge. I-217 left host-to-guest unlimited on purpose (to avoid capping
cache downloads), but did not weigh cross-tenant NIC contention. Fairness
issue, no boundary crossed. Fix if wanted: a per-tap egress HTB with a
generous ceiling that exempts the caches, or fq_codel per guest (needs a
new decision, since it reverses part of I-217).

## S-36 (low) Console log flood evicts other tenants' logs from the shared Fluent Bit buffer

Location: `internal/hostd/console/console.go:18-22` (rotation only, no
rate limit), `nix/hosts/fluent-bit.nix` (one Loki output, 1G buffer that
drops the oldest chunks; the host journal shares it),
`ops/loki/retention.yaml:34-42` (per-stream and ingestion limits
commented out).

A guest writing continuously to its serial console consumes the shared
buffer; when the output backs up (a Loki outage or a 429), the oldest
chunks are dropped, which can be other guests' console lines or the host
journal. Shipping is off today (no Loki recorded). Measured serial
throughput on this guest is ~35 KB/s, so one guest fills the 1G buffer in
~8h of outage; the durable cost is Loki storage (~3 GB/day/guest for 30
days). Fix: a per-guest throttle (Fluent Bit filter keyed on guest_id, or
a token bucket in the Tailer), a separate output/budget for the host
journal, and uncomment the Loki per-stream limits.

## S-37 (low) `prepareAuthShare` follows a symlink at `virtiofsd-auth` and chowns/chmods the target as root

Attacker: code running as the `hostd` user (a compromised Cloud
Hypervisor after a VMM escape), or `repose-auth` outside its sandbox. A
guest needs a VMM escape first.

Location: `internal/hostd/guest/claudeauth.go:71` (socket dir =
`<guest dir>/virtiofsd-auth`), `:73-83` (`MkdirAll`/`Chown`/`Chmod`
follow a symlink), `internal/hostd/guest/unit.go:112-120` (the guest dir
is `root:hostd 01770`, writable by the hypervisor user).

Attack path: when `virtiofsd-auth` is absent (a guest with no user id, or
`NoAuthShare`), a process running as the hypervisor user can create it as
a symlink, and the next `prepareAuthShare` chowns the link's target to
`repose-auth:hostd 0750`. Retargeting to `/var/lib/repose/hostd` or
another user's `claude-auth` hands that directory to `repose-auth` and
makes it readable by every hostd-group process. The store socket dir uses
the same pattern but is created before the hypervisor first runs and is
owned by `virtiofsd`, so the sticky bit protects it.

Evidence: reproduced with the package's own create path; through the
planted symlink the victim dir's mode changed from 0700 to 0750 (on a
host, `hostd` runs as root so the chown to `repose-auth:hostd` takes
effect). The restore trigger the original finding listed does not hold
(destroy removes the guest dir first); the real triggers are an operator
re-enabling `--claude-login-share` on guests that booted without it, and a
`repose-auth` compromise.

Fix: `Lstat` first and refuse or `os.Remove` any entry that is not a real
directory, then create with `Mkdir` and `Fchown`/`Fchmod` on an fd opened
`O_DIRECTORY|O_NOFOLLOW`. Better, create the per-guest socket dirs under a
root-owned `0711` parent the hypervisor cannot write. Apply the same to
the store socket dir and to `Chown(dir)` at `unit.go:115`.

## Coverage gaps

- No production testing: 8444 reachability, IMDS reachability from a host
  netns, and the end-to-end S-1/S-2 chains were read, not executed, per
  the rules.
- Loki/Fluent Bit shipping is off, so S-36's eviction was reasoned, not
  triggered, and the never-log list was not checked against a live store.
- The gateway connection-slot and conntrack exhaustion (S-6, S-13) were
  confirmed in code and one local repro (S-6); no flood was sent.
- The host-side disk-IO and thin-pool fills (S-12, S-15) were confirmed
  in code and (for dm-thin) a loop-device repro; not run against a real
  host, which would DoS neighbours.
- Review of the dashboard's client code was limited to the CSP/framing
  question (a hardening note, left out here as no attack path survived in
  default browsers) and the SSRF below.
- ntfy SSRF (`ntfy_url`): confirmed a blind SSRF with a one-bit status
  oracle from the api's network position; the Metadata header cannot be
  set so IMDS token theft fails, and reachable internal services need mTLS
  or a token. Low. Fix: a `net.Dialer.Control` hook refusing loopback,
  private, link-local, CGNAT and mesh addresses, `CheckRedirect` refusing
  redirects. Not promoted to the main table because the impact is a
  reachability oracle, not data exposure.

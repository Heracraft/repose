# 02: Guest base image

Milestone: M1. Owns `interfaces/guest-conventions.md`. Consumes
`interfaces/vsock-guestd.md` (guestd is installed and enabled here, built by
04). Consumed by 03-hostd (builds and runs the output), 07-cli (relies on
every convention), 12-nix-config-pipeline (composes the user fragment on top
of this module).

## 1. Goal

Define the NixOS module every guest gets regardless of user config, and the
microvm.nix wiring that turns a NixOS configuration into a Cloud Hypervisor
runner using the host's shared store. Everything in
`interfaces/guest-conventions.md` and `DESIGN.md` §5 is produced here.

## 5. Design detail

### The shared store and the overlay

The guest mounts the host's export read-only at `/nix/.ro-store` and an
overlay with the writable upper dir on the thin volume at `/nix/.rw-store`,
presenting `/nix/store` as the union. microvm.nix's `writableStoreOverlay`
does this. The guest can therefore run `nix-shell` and `nix profile install`
for things not in the host store; those go to the overlay and are the
guest's own (and count toward its volume). The guest's `nix-daemon` runs
with `substituters` = cache.nixos.org by default, `sandbox = true`, and
cannot see the host daemon. dev is a trusted user (dev has passwordless sudo
anyway), so a project may add its own caches (DECISIONS I-530). It builds inside its own vCPU and RAM caps, so a user
running a heavy `nix build` in a shell affects only themselves. This is
distinct from the config pipeline (12), where the host builds the system.

Consequence: a path the host garbage-collects while a guest overlay refers
to it breaks that guest. hostd roots every guest's system closure (01, 03),
and anything the user installed into the overlay is either in the overlay's
upper dir (safe) or a host path referenced by a guest profile. The second
case is closed by having the guest's `nix-daemon` copy any host path it
references into the overlay on install (`nix.settings.auto-optimise-store =
false`, and a guest-side `repose-pin-profile` activation hook that runs
`nix copy --to local?root=/nix/.rw-store` for the profile closure). The VM
test covers this: install a package into the profile, delete it from the
"host" store, the profile still runs.

A binary built in the guest (cc, cgo, node-gyp, cargo) names base store
paths directly: the gcc wrapper's glibc as its interpreter, gcc-lib and the
`PKG_CONFIG_PATH` libraries in its RUNPATH. `repose-pin-profile` copies
the closures of those link targets up too, at every boot and switch, and
roots each under `/nix/var/nix/gcroots/repose-link-targets/`, so a binary
in a checkout keeps running after a base change and a host GC (DECISIONS
I-533). An unchanged glibc costs nothing; a new one costs its closure in
the upper dir (about 36 MiB for glibc, 9 MiB for openssl).

Deleting a path the lower layer also has leaves a whiteout in the upper
dir that hides the host's copy. guestd roots every path the lower layer
serves that the guest's database lists, under
`/nix/var/nix/gcroots/repose-view/`, at every registration and at its
start, so a whole-store GC (`nix-collect-garbage`, `nix store gc`) deletes
none of them (DECISIONS I-588); stage 1 removes every whiteout in the
upper store dir before stage 2, so a start repairs what a deletion that
ignored the roots did (I-587); and `Switch` to a closure a whiteout hides
fails saying so (I-589). The base still schedules no whole-store GC:
`repose-store-gc.timer` deletes, weekly, dev's profile generations older
than 14 days and then the dead paths that exist in the upper dir alone
(DECISIONS I-529).

### Why the fragment is home-manager, and where it lands

The base is a NixOS module; the user's fragment is a home-manager module
applied to `dev` through `home-manager.nixosModules.home-manager` with
`useGlobalPkgs = true` and `useUserPackages = true`. The fragment cannot
touch system services, users, networking, kernel or sshd because it is a
home-manager module, and the platform's `nixosSystem` call passes it only
there. Users who need a system service (Postgres, Redis) get it from the
menu catalog (12), which renders to a platform-controlled NixOS snippet
with an allowlist of services. That boundary is what makes "user Nix on a
shared host" defensible: the fragment can install anything into the home
profile and nothing outside it.

### The ssh host key is a secret

The guest's host key must be stable across restarts (or the CLI's
known_hosts would churn) and signed by the Host CA. hostd generates it at
`CreateGuest`, asks the api to sign it, and delivers both through the
secrets tmpfs mechanism with the reserved names `ssh_host_ed25519_key` and
`ssh_host_ed25519_key-cert.pub`. An activation script symlinks them into
`/etc/ssh/`. Reserved names are rejected by `PUT /secrets` (05).

### Agent wrappers and hooks

`wrap.nix` produces, for each agent, a script that sets `TERM`, `COLORTERM`,
merges platform hook config on first run, and execs the real binary with
`"$@"`. The merge is a `jq` deep merge that adds the `repose-hook` entries
under `hooks.Notification` and `hooks.Stop` (Claude Code) only if no entry
with `repose-hook` in its command exists. For agents without a hook system
(pi, and opencode until it has one), guestd's `AgentState` heuristic (tmux
pane idle with the agent process alive and the last line ending in a prompt
marker) produces `needs_input` and `completed` events; `features/agents.md`
documents per-agent accuracy.

### noVNC chain

Socket activation keeps the desktop's memory cost at zero until asked.
`repose browser` forwards 6080; the page connects; systemd starts a
`systemd-socket-proxyd` service that requires websockify, which pulls in
Xvnc, openbox and the agents' browser (DECISIONS I-33, I-246, I-292).
Chromium launched by the agent with `DISPLAY=:99` (the profile snippet
exports it when the display is up) appears on that desktop. When the
agent runs headless Chromium, nothing is displayed and nothing is started.

### Docker address pools

Docker's default `172.17.0.0/16` and the compose pools would not collide
with `10.64.0.0/12` today, but a user's compose file with `10.64.x.x` would.
Pinning `default-address-pools` to `172.20.0.0/14` makes the collision
impossible rather than unlikely.

### Retiring `packages/core/flake.nix`

The current dev box runs from that flake with `home-manager switch`. After
`tools.nix` exists: (1) `nix/flake.nix` exposes `devShells.default` with the
same tools; (2) the dev box switches to it; (3) `packages/core/` is deleted
and `pnpm-workspace.yaml` no longer lists it. Until (2) is confirmed on the
dev box, the flake stays.

## 6. Failure modes

| Failure | Outcome |
|---|---|
| Guest boots but sshd refuses the certificate | `AuthorizedPrincipalsFile` missing or wrong principal. guestd's `SetPrincipals` writes it; if guestd never ran, `Ready` was never sent and the api shows the guest as `starting`, then `error` after 120 s with `guest did not become ready`. The console log (hostd) shows the sshd error. |
| `/nix/store` union missing paths | virtiofs share not mounted or wrong tag. Guest journal: `mount: /nix/.ro-store: wrong fs type`. hostd reports `guest_unresponsive` after Ping fails; console log has the mount error. |
| Docker fails with `overlay2 not supported` | Kernel module list wrong or the volume is not ext4. VM test catches it; in production it is a base bug, guests are not affected until they are switched to the new base, and `hold_base_updates` exists for this. |
| Agent wrapper clobbers a user hook | Forbidden by the merge rule; VM test asserts an existing hook survives. |
| Xvnc starts but Chromium shows nothing | `DISPLAY` not exported because the profile snippet ran before Xvnc. The snippet checks the X socket each shell start; the user opens a new shell. Documented in `features/browser.md`. |
| A user profile references a host path that gets collected | `repose-pin-profile` copies profile closures into the overlay; if it did not run (activation failed), the error is `nix: path /nix/store/... does not exist` in the guest; the fix is `nix profile install` again, and the base bug is filed. |
| Guest OOM | zram absorbs bursts; MGLRU's `min_ttl_ms` makes the kernel kill rather than thrash; the kernel OOM killer picks the largest process not on the keystroke path or an agent, which is usually a build (I-200, I-576). guestd sends `Warning{kind: "oom"}` from `dmesg`, and the user sees it in `repose status`. |

## 7. Testing

- `nix flake check` runs `nix/guest/tests/` on QEMU with a fake shared
  store (a squashfs of the closure mounted read-only at `/nix/.ro-store`)
  so the overlay logic is tested without CH.
- On a real host with 03: create a guest with the base and no fragment,
  run every command in the checklist from inside it.
- Size: the base closure must be under 6 GB (checked in CI with `nix
  path-info -S`); a bigger base means every host's store grows and every
  first-boot copy of the closure metadata takes longer. Fail the check
  above 6 GB and record the offender.

## 8. Rollback

A bad base version is rolled back by re-applying the previous
`base_versions` row: the api sends `ApplyConfig` with the previous closure
(still rooted for 14 days) to every guest not on hold. The base bump job
(12) records the previous version so this is one admin command:
`repose-admin base rollback <version>`.
